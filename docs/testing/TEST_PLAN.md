# Test Plan — фронтенд AI-ревьюера

Стратегия и уровни тестирования интерфейса: просмотр одного прогона ревью, дифф, свёрнутый
контекст, inline-замечания и технический trace прогона. Слои, компоненты и модели — в
[`FRONTEND_ARCHITECTURE.md`](../../FRONTEND_ARCHITECTURE.md), ревизия 5.0 — готовится в
[dmc-268-ui-t1#6](https://github.com/larchanka-training/dmc-268-ui-t1/pull/6). План правится в
том же PR, что меняет описанное там поведение.

## 1. Риски, ради которых существует план

Интерфейс ревью читают по строкам кода, поэтому почти все риски здесь — про точность
отображения, а не про верстку.

| ID  | Риск                                                                                     | Проявление                                                 | Где защита                                                                     |
| --- | ---------------------------------------------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------ |
| R-1 | **Дифф отображается неверно**: съехали номера строк, перепутаны стороны, потеряна строка | разработчик читает не тот код и не верит ревью             | unit на сборку диффа, компонентные тесты `DiffViewer`, `DiffHunk` и `DiffLine` |
| R-2 | **Замечание привязано не к той строке**                                                  | замечание висит на чужой строке — хуже, чем его отсутствие | компонентные тесты `ReviewCommentThread`, интеграционные на `ReviewRunView`    |
| R-3 | **Два источника правды**: данные adapter продублированы в Zustand                        | после обновления данных экран показывает старое            | тесты фич и интеграционные: состояние интерфейса переживает refetch            |
| R-4 | **Не показаны loading, error и пустые состояния**                                        | белый экран вместо «ревью ещё идёт» или «замечаний нет»    | обязательные четыре состояния в каждом тесте запроса данных                    |
| R-5 | **Контракт с backend разъехался**: mock adapter не совпадает с тем, что придёт от API    | локально работает, на стенде пусто                         | контрактные тесты на границе adapter                                           |

Отдельно — **размер диффа**: 200 файлов и файл на тысячи строк — нормальный вход, а не крайний
случай. Производительность проверяется как требование, а не как впечатление (§3.8).

## 2. Область

**В области:** экран одного прогона `ReviewRunView` — метаданные и статус прогона, сводка,
список файлов, `DiffViewer` в режимах unified и side-by-side, свёрнутый контекст внутри
`DiffHunk`, inline-замечания и статус их публикации, фильтр замечаний по severity,
`RunInspector` на mock-действиях; состояние приложения, граница с adapter, доступность и
поведение на больших диффах.

**Вне области:** то, что архитектура (§1.3) выносит за границу задачи, — маршруты, HTTP API,
механизм обновления прогона (polling), интеграция с Git-хостингом, авторизация. Сам AI-ревьюер
и качество его замечаний — это план тестирования бэкенда команды 1 в
[dmc-268-api-t1#7](https://github.com/larchanka-training/dmc-268-api-t1/pull/7). SSR —
приложение собирается как SPA.

### 2.1 Что план берёт из архитектуры и правил

- **FSD и направление импортов.** Тест живёт на том же уровне, что и поведение: чистая
  логика — рядом с модулем, компонент — рядом с компонентом, сценарий — в `features`, связка
  виджетов — рядом с `ReviewRunView`. Тест не импортирует внутренности чужого слайса: у слайса
  один публичный вход, `index.ts`.
- **Подменяется adapter данных, а не `fetch`.** У mock adapter та же граница, что у будущего
  HTTP-клиента, поэтому тест не знает про транспорт и переживает его появление.
- **Разделение состояния** (FE-DEC-03). Данные adapter — в TanStack Query; выбранный файл,
  фильтры severity, режим viewer, раскрытый контекст и выбранное действие — в Zustand; hover и
  popover одной строки — локально. Тест на фичу проверяет, что состояние интерфейса не
  дублирует кэш и переживает его обновление.
- **Запрос по роли и тексту.** Селектор по классу Tailwind или по имени компонента ломается на
  рефакторинге без изменения поведения; `data-testid` допустим там, где у элемента нет
  доступной роли.
- **Три антипаттерна из скилла `frontend-tdd`** считаются дефектом ревью: тест реализации,
  тавтологический тест, снапшот вместо утверждения. Скилл и правила слоёв лежат в `.agents/`.

## 3. Уровни

**L0. Статика [действует].** `pnpm run typecheck`, `lint`, `stylelint`, `format:check`. Типы
несут часть нагрузки тестов: доменные модели описаны точно, поэтому «дифф без стороны
строки» не собирается, а не падает в рантайме.

Направление импортов между слоями FSD сейчас держится на договорённости. Правило проверяемо
линтером и должно ронять сборку, а не ждать ревьюера — это OpenSpec-change
`fsd-import-boundaries` для спеки `code-quality` (§5.1).

### 3.1 Unit [действует]

Чистая логика без DOM: сборка представления диффа из `DiffFile`, раскладка строк hunk в две
колонки для side-by-side, свёрнутые диапазоны контекста по `is_collapsed_context`, фильтры по
severity и файлу, привязка замечания к строке по `file_path`, `side` и номеру строки,
форматтеры, Zod-валидация моделей adapter.

- прямой вызов функции, без рендера;
- краевые входы обязательны: пустой дифф, файл без изменений, только удаления,
  переименование, бинарный файл (ZIP), не-UTF8, дифф с одной строкой;
- границы диапазонов: первая и последняя строка hunk, соседние hunks без зазора, свёрнутый
  контекст в начале и в конце файла.

### 3.2 Компонентные [действует частично]

Vitest + React Testing Library, рендер и действия пользователя. На `develop` есть только
smoke-тест стартового `App`. По одному набору на каждый компонент из §5.2 архитектуры:

| Компонент             | Что обязан проверить тест                                                                                                                                                                                                                                                                      |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RunHeader`           | каждый из семи статусов даёт свой доступный текст, а не только цвет; **`cancelled` читается как завершённый, а не как идущий**; незнакомое значение не ломает экран (§3.5); `failure_reason` показан, когда он есть; пустые `model`, `tokens_used`, `duration_seconds` не выводятся как `null` |
| `ReviewSummary`       | число замечаний по каждой severity совпадает с входными данными; показаны отклонённые валидацией и статусы публикации; замечание без корректной привязки к строке показано здесь, а не в коде                                                                                                  |
| `ReviewWorkspace`     | передаёт в `DiffViewer` замечания только выбранного файла; выбор файла, фильтры и режим берёт из Zustand и не хранит копию диффа                                                                                                                                                               |
| `FileList`            | видны все изменённые файлы, включая файлы без замечаний; выбран ровно один файл; путь, статус, additions/deletions и число замечаний на своих местах; выбор меняет `selected_file`                                                                                                             |
| `DiffViewer`          | рендерит **один** выбранный `DiffFile`; unified сохраняет исходный порядок строк; side-by-side ставит удалённые и добавленные строки одного hunk друг напротив друга; смена режима не меняет данные; бинарный файл не показан как текст                                                        |
| `DiffHunk`            | заголовок `@@` с диапазонами; строки в порядке диффа; свёрнутый контекст раскрывается и показывает именно скрытые строки; повторное раскрытие их не дублирует; раскрытие одного блока не раскрывает другой hunk                                                                                |
| `DiffLine`            | added, removed и context различимы не только цветом; номера старой и новой стороны на своих местах; замечание передаётся дальше только при совпадении `file_path`, `side` и номера строки                                                                                                      |
| `ReviewCommentThread` | показывает текст, severity текстом, suggestion и статус `PublishedComment`; замечание к удалённой строке — на старой стороне; без публикации это видно явно                                                                                                                                    |
| `RunInspector`        | действия упорядочены по `position`; незнакомый `tool` показан нейтрально и не ломает список                                                                                                                                                                                                    |
| `ActionTree`          | `tool`, статус, время и длительность каждого действия; выбор действия меняет `selected_action_id`                                                                                                                                                                                              |
| `ActionDetails`       | показывает только очищенные `request_preview`, `response_preview` и ошибку; `unknown`-preview в виде JSON, текста и `null` не ломает разметку; полный payload не загружается                                                                                                                   |

### 3.3 Фичевые [целевое]

Сценарий целиком, с mock adapter: фильтрация замечаний по severity (`features/filter-findings`),
выбор файла, раскрытие свёрнутого контекста, выбор действия в `RunInspector`. Проверяется
результат для пользователя, а не вызовы стора.

### 3.4 Интеграционные [целевое]

Рендер `ReviewRunView` с подменённым adapter. Обязательные состояния каждого запроса данных —
**loading, error, empty и данные**; отсутствие любого из них считается незакрытой веткой, как
необработанный `else` в бэкенде.

| ID     | Сценарий                                                                             | Ожидание                                                                           |
| ------ | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| INT-01 | прогон завершён, есть замечания                                                      | файлы, дифф и замечания на своих строках и сторонах                                |
| INT-02 | прогон не завершён — adapter отдаёт `building_context`, `analysing` или `publishing` | любой из них показан как идущий, дифф не притворяется полным                       |
| INT-03 | прогон `failed`                                                                      | причина показана, пустой экран не выдаётся за успех                                |
| INT-04 | замечаний нет                                                                        | явное «замечаний нет», а не пустая область                                         |
| INT-05 | adapter ответил ошибкой или данными вне схемы                                        | сообщение и возможность повторить, приложение не падает                            |
| INT-06 | данные обновились после refetch                                                      | выбранный файл, режим viewer и раскрытый контекст сохранились (R-3)                |
| INT-07 | прогон `cancelled`                                                                   | показан как отменённый и завершённый, а не идущий; результат не выдаётся за полный |
| INT-08 | статус вне известного набора                                                         | прогон показан идущим, экран не падает — запасной путь только для новых значений   |

### 3.5 Контрактные [целевое]

Граница с backend — единственное место, где фронтенд может разойтись с чужой командой молча.

- mock adapter и будущий HTTP-клиент реализуют один интерфейс; тест гоняет один набор
  утверждений против обоих;
- фикстуры валидируются теми же Zod-схемами, что и ответ adapter: поле, которого нет в модели,
  роняет тест, а не появляется в UI как `undefined`;
- `ReviewRun`, `ReviewFinding` и `PublishedComment` повторяют доменные значения backend
  (FE-CON-04), поэтому их фикстуры сверяются с `app/domain` в `dmc-268-api-t1`. Diff-модели и
  `ReviewRunAction` — UI mock-модели (FE-CON-05, FE-CON-06): их фикстуры фиксируют
  **предположение** фронтенда и сверяются в тот же день, когда появится browser-контракт.

**Статусы прогона.** Архитектура перечисляет те же семь значений, что `ReviewRunStatus` в
`app/domain/enums.py`: `queued`, `building_context`, `analysing`, `publishing`, `completed`,
`failed`, `cancelled`. Отображение у них явное, и сценарии разделены по смыслу, а не по
незнакомости:

- **`cancelled` — терминальный статус.** Бэкенд отменяет прогон, когда в тот же PR приходит
  новый push: старый переходит в `cancelled` и находок больше не публикует. Если UI покажет
  его идущим, пользователь будет ждать результата, которого не будет. Это INT-07.
- **Запасной путь — только для действительно новых значений.** Чужой enum будет расти:
  незнакомое значение показывается идущим и не роняет экран (INT-08).

### 3.6 E2E [целевое]

Playwright, появляется вместе с рабочим backend — OpenSpec-change `e2e-playwright` (§5.1).
Дымовой набор, а не копия интеграционных: открыть прогон, выбрать файл, раскрыть контекст,
увидеть замечание, отфильтровать по severity. Плюс проверка на реальном браузере того, чего не
видит jsdom: прокрутка длинного диффа, фокус при навигации с клавиатуры.

### 3.7 Доступность [целевое]

Не отдельная фаза, а проверки внутри компонентных тестов: обход по клавиатуре до любого
действия, видимый фокус, роли и доступные имена у переключателя режима, фильтров и раскрытия
контекста, статус и severity читаются текстом, а не только цветом. Автоматическая проверка
(`axe`) ловит часть и подключается вместе с `e2e-playwright`; остальное — чек-лист в ревью.

### 3.8 Производительность [целевое]

Два эталонных входа — по одному на каждое узкое место, иначе при провале непонятно, что
чинить. Оба лежат в `src/test/fixtures` и не меняются между прогонами.

| Вход     | Состав                          | Что меряем                               | Порог                    |
| -------- | ------------------------------- | ---------------------------------------- | ------------------------ |
| `PERF-A` | один файл на 5000 строк         | время до первого отображения диффа файла | p95 ≤ 2 с                |
| `PERF-A` | тот же файл, свёрнутый контекст | раскрытие одного свёрнутого блока        | p95 ≤ 200 мс             |
| `PERF-A` | тот же файл                     | прокрутка                                | нет кадров дольше 100 мс |
| `PERF-B` | 200 файлов по 20 строк          | время до отображения `FileList`          | p95 ≤ 1 с                |
| `PERF-B` | те же файлы                     | переключение выбранного файла            | p95 ≤ 200 мс             |

Как мерить: 10 прогонов, `performance.mark` от старта рендера до появления первой строки или
элемента списка; прокрутка — в Playwright, а не в jsdom. Условия фиксированы, иначе цифры
несравнимы: CI-раннер, production-сборка, холодный кэш. В отчёте — p95 и число прогонов.

Цифры стартовые. **Первый замер устанавливает baseline**, со второго релиза отклонение больше
20 % от предыдущего — регресс. Провал `PERF-A` — повод для решения о виртуализации строк
(архитектура §11 откладывает его до замера на реальных объёмах), провал `PERF-B` — о
виртуализации списка файлов. Порог ради этого не ослабляется.

## 4. Тестовые данные

| Класс          | Как устроен                                                                                                                                                                                   |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Фикстуры диффа | в `src/test/fixtures`: маленький дифф, многофайловый, только удаления, переименование, бинарный (ZIP), свёрнутый контекст в начале, середине и конце файла, `PERF-A` и `PERF-B`               |
| Фабрики        | в `src/test/factories.ts`: `ReviewRun`, `DiffFile`, `DiffHunk`, `DiffLine`, `ReviewFinding`, `PublishedComment`, `ReviewRunAction` — идентификаторы и время аргументами, а не из `Date.now()` |
| Mock adapter   | живёт в `app/mocks` (архитектура §5.1) и реализует границу данных; тест подменяет его, а не `fetch`                                                                                           |

`ReviewFinding` и `PublishedComment` — разные сущности (§8.2 архитектуры): замечание модели и
факт его публикации, поэтому и фабрики раздельные. Фикстуры не содержат чужого кода и
персональных данных: содержимое диффов синтетическое. Время и идентификаторы фиксированы, иначе
тест начинает падать по календарю.

## 5. Гейты

**Мёрж PR:** `typecheck`, `lint`, `stylelint`, `format:check` зелёные; `pnpm run test` проходит
целиком; у нового компонента есть тест на отображение и на действие пользователя; у нового
запроса данных закрыты четыре состояния; покрытие не ниже порога — с момента, когда порог
задан (§5.1).

Не проходит ревью, даже если тесты зелёные: селектор по классу или имени компонента, снапшот
без утверждения, тавтологический тест, мок `fetch` вместо подмены adapter.

**Релиз:** интеграционные INT-01…INT-08 проходят; дымовой E2E зелёный; проверка доступности без
нарушений на экране `ReviewRunView` — единственном в архитектуре; пороги из §3.8 держатся на
`PERF-A` и `PERF-B`, начиная со второго релиза — с отклонением от предыдущего не больше 20 %.

**CI сегодня.** На `develop` три джоба: `syntax` (typecheck), `lint` и `test`;
[#14](https://github.com/larchanka-training/dmc-268-ui-t1/pull/14) добавляет четвёртый,
`terraform`. `stylelint`, `format:check` и сбор покрытия в CI не входят. `format:check` на
`develop` падает на `.github/workflows/ci.yml` и `eslint.config.js`, поэтому включать его в
блокирующий гейт можно только после разовой чистки этих двух файлов — иначе первый же PR
встанет из-за чужих файлов.

### 5.1 Что требует OpenSpec-change

Эти пункты меняют спекнутые возможности, поэтому по `AGENTS.md` идут отдельными change'ами, а не
прозой этого плана:

| Change                  | Спеки                                               | Что меняет                                                                                                                                            |
| ----------------------- | --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `testing-coverage-gate` | `testing`                                           | `test.coverage.thresholds` в `vite.config.ts`: 70 % строк в целом, 90 % для `src/shared/**` и `src/entities/**` через ключи-глобы; сбор покрытия в CI |
| `ci-style-gates`        | `code-quality`, `git-hooks`                         | джобы `stylelint` и `format:check` отдельными джобами, а не шагами одной: совмещённая сообщает один провал на две несвязанные причины                 |
| `fsd-import-boundaries` | `code-quality`                                      | проверка направления импортов FSD линтером (`import/no-restricted-paths` или `eslint-plugin-boundaries`)                                              |
| `e2e-playwright`        | `dependency-management`, `build-tooling`, `testing` | Playwright и `axe`, дымовой E2E и замеры §3.8                                                                                                         |

Порог покрытия повышается по мере роста кода и не опускается без записанного решения в PR. До
мержа `testing-coverage-gate` пункт «покрытие не ниже порога» не действует: порога нет ни в
`vite.config.ts`, ни в спеке `testing`.

## 6. Шаблон тест-кейса

```
ID:              <УРОВЕНЬ>-<номер>        UNIT-007, INT-03, E2E-02, PERF-A
Уровень:         Unit | Компонентный | Фичевый | Интеграционный | Контрактный | E2E | Производительность
Риск:            R-1 … R-5
Предусловия:     данные adapter, состояние стора, размер окна
Шаги:            1. … 2. …
Ожидание:        что видит и может сделать пользователь
Не ожидается:    дубль замечания, потеря раскрытого контекста, белый экран
Автоматизирован: путь к тесту | нет + причина
```

Ответственность: разработчик — unit и компонентные тесты на свой код; QA — интеграционные,
контрактные, E2E и доступность; DevOps — джобы CI.
