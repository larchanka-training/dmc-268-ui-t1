# Test Plan — фронтенд AI-ревьюера

Стратегия и уровни тестирования интерфейса: просмотр прогона ревью, дифф, контекст и
inline-замечания. Архитектура, слои и модели — в
[`FRONTEND_ARCHITECTURE.md`](../../FRONTEND_ARCHITECTURE.md) — готовится в
[dmc-268-ui-t1#6](https://github.com/larchanka-training/dmc-268-ui-t1/pull/6).

## 1. Риски, ради которых существует план

Интерфейс ревью читают по строкам кода, поэтому почти все риски здесь — про точность
отображения, а не про верстку.

| ID | Риск | Проявление | Где защита |
|---|---|---|---|
| R-1 | **Дифф отображается неверно**: съехали номера строк, перепутаны стороны, потеряна строка | разработчик читает не тот код и не верит ревью | unit на сборку диффа, компонентные тесты `DiffHunk` и `DiffLine` |
| R-2 | **Комментарий привязан не к той строке** | замечание висит на чужой строке — хуже, чем его отсутствие | компонентные тесты `ReviewCommentThread`, интеграционные на странице |
| R-3 | **Два источника правды**: серверные данные продублированы в Zustand | после обновления данных экран показывает старое | тесты фич и интеграционные: инвалидация Query, состояние UI переживает refetch |
| R-4 | **Не показаны loading, error и пустые состояния** | белый экран вместо «ревью ещё идёт» или «замечаний нет» | обязательные три состояния в каждом query-тесте |
| R-5 | **Контракт с backend разъехался**: mock adapter не совпадает с реальным API | локально работает, на стенде пусто | контрактные тесты на границе адаптера |

Отдельно — **размер диффа**: 200 файлов и тысячи строк это нормальный вход, а не крайний
случай. Производительность проверяется как требование, а не как впечатление.

## 2. Область

**В области:** отображение прогона ревью и его статусов, diff-компоненты, inline-замечания
и треды, раскрытие контекста, фильтрация, состояние приложения, граница с API (mock adapter
и будущий HTTP-клиент), доступность и поведение на больших диффах.

**Вне области:** сам AI-ревьюер и качество его замечаний — это план тестирования бэкенда
команды 1, готовится в
[dmc-268-api-t1#7](https://github.com/larchanka-training/dmc-268-api-t1/pull/7);
аутентификация и биллинг, пока их нет в интерфейсе; SSR — приложение собирается как SPA.

### 2.1 Что план берёт из архитектуры

- **FSD и направление импортов.** Тест живёт на том же уровне, что и поведение: чистая
  логика — рядом с модулем, компонент — рядом с компонентом, сценарий — в `features`,
  связка слоёв — в `pages`. Тест не импортирует внутренности чужого слайса: у слайса один
  публичный вход, `index.ts`.
- **Подменяется адаптер данных, а не `fetch`.** У mock adapter та же граница, что у
  будущего HTTP-клиента, поэтому тест не знает про транспорт и переживает его появление.
- **Разделение состояния.** Серверные данные — в TanStack Query, состояние интерфейса — в
  Zustand, состояние одного компонента — локальное. Тест на фичу проверяет, что выбранный
  файл и раскрытый контекст не дублируют то, что уже есть в кэше.
- **Запрос по роли и тексту.** Селектор по классу Tailwind или по имени компонента ломается
  на рефакторинге без изменения поведения; `data-testid` допустим там, где у элемента нет
  доступной роли.
- **Три антипаттерна из скилла `frontend-tdd`** считаются дефектом ревью: тест
  реализации, тавтологический тест, снапшот вместо утверждения. Скилл и правила слоёв
  готовятся в [dmc-268-ui-t1#8](https://github.com/larchanka-training/dmc-268-ui-t1/pull/8).

## 3. Уровни

**L0. Статика [действует].** `pnpm run typecheck`, `lint`, `stylelint`, `format:check`.
Типы здесь несут часть нагрузки тестов: доменные модели описаны точно, поэтому «дифф без
стороны строки» не собирается, а не падает в рантайме.

Чего не хватает: направление импортов между слоями FSD сейчас держится на договорённости.
Правило проверяемо линтером (`import/no-restricted-paths` или `eslint-plugin-boundaries`) —
предлагается включить отдельным PR, потому что нарушение слоёв должно ронять сборку, а не
ждать ревьюера.

### 3.1 Unit [действует]

Чистая логика без DOM: сборка диффа из ответа API, вычисление скрытых диапазонов контекста,
фильтры по severity и файлу, форматтеры, маппинг API → доменные модели.

- прямой вызов функции, без рендера;
- краевые входы обязательны: пустой дифф, файл без изменений, только удаления, переименование,
  бинарный файл, не-UTF8, дифф с одной строкой;
- границы диапазонов: первая и последняя строка ханка, соседние ханки без зазора,
  раскрытие контекста в начале и в конце файла.

### 3.2 Компонентные [действует частично]

Vitest + React Testing Library, рендер и действия пользователя. Уже есть smoke-тест `App`.
По одному набору на каждый базовый компонент из архитектуры:

| Компонент | Что обязан проверить тест |
|---|---|
| `CodeBlock` | нумерация строк непрерывна, длинная строка не ломает разметку, прокрутка не теряет номера |
| `DiffViewer` | порядок файлов, выбор файла меняет содержимое, комментарии попадают к своим строкам |
| `DiffHunk` | заголовок с диапазонами, строки в порядке диффа, зазор между ханками обозначен |
| `DiffLine` | added, removed и context различимы не только цветом; номера старой и новой стороны на своих местах; у строки есть точка привязки комментария |
| `ReviewCommentThread` | замечание рядом с целевой строкой нового диффа, ответы в порядке, severity видна текстом |
| `ContextExpander` | раскрытие показывает именно скрытые строки, повторное раскрытие не дублирует их, состояние уходит в Zustand |
| `ReviewRunStatus` | каждый статус даёт разный доступный текст, а не только цвет; **незнакомое значение не ломает экран** (см. §3.5) |

### 3.3 Фичевые [целевое]

Сценарий целиком, с mock adapter: раскрытие контекста, фильтрация замечаний по severity,
выбор файла. Проверяется результат для пользователя, а не вызовы стора.

### 3.4 Интеграционные [целевое]

Рендер страницы `review-run` с подменённым транспортом. Обязательные состояния каждого
запроса — **loading, error, empty и данные**; отсутствие любого из них считается незакрытой
веткой, как необработанный `else` в бэкенде.

| ID | Сценарий | Ожидание |
|---|---|---|
| INT-01 | прогон завершён, есть замечания | файлы, дифф и замечания на своих строках |
| INT-02 | прогон в статусе `in_progress` | статус виден, дифф не притворяется полным |
| INT-03 | прогон `failed` | причина показана, пустой экран не выдаётся за успех |
| INT-04 | замечаний нет | явное «замечаний нет», а не пустая область |
| INT-05 | API ответил ошибкой | сообщение и возможность повторить, приложение не падает |
| INT-06 | данные обновились после refetch | выбранный файл и раскрытый контекст сохранились (R-3) |

### 3.5 Контрактные [целевое]

Граница с backend — единственное место, где фронтенд может разойтись с чужой командой
молча.

- mock adapter и HTTP-клиент реализуют один и тот же интерфейс; тест гоняет один набор
  утверждений против обоих;
- фикстуры валидируются схемой доменных моделей: поле, которого нет в контракте, роняет
  тест, а не появляется в UI как `undefined`;
- фикстуры берутся из формата ответа backend-репозитория, а не выдумываются: расхождение
  форматов — это дефект, который дешевле поймать здесь. Пока эндпоинтов ревью в backend нет,
  фикстуры фиксируют **предположение** фронтенда, и их придётся сверить в тот же день,
  когда контракт появится.

**Известное расхождение, которое ждёт решения.** Фронтенд-архитектура знает четыре статуса
прогона — `queued`, `in_progress`, `completed`, `failed`. Модель данных бэкенда команды 1
(`dmc-268-api-t1`) описывает семь:
`queued`, `building_context`, `analysing`, `publishing`, `completed`, `failed`, `cancelled`,
и значения `in_progress` там нет вообще. То есть сегодня три реальных статуса не имеют
отображения, а один нарисованный не придёт никогда. До согласования контракта UI обязан
переживать незнакомое значение статуса: показать прогон как идущий и не падать. Тест на
это обязателен — он останется полезным и после согласования.

### 3.6 E2E [целевое]

Playwright, появляется вместе с рабочим backend. Дымовой набор, а не копия интеграционных:
открыть прогон, выбрать файл, раскрыть контекст, увидеть замечание, отфильтровать по
severity. Плюс проверка на реальном браузере того, чего не видит jsdom: прокрутка длинного
диффа, sticky-заголовки, фокус при навигации с клавиатуры.

### 3.7 Доступность [целевое]

Не отдельная фаза, а проверки внутри компонентных тестов: обход по клавиатуре до любого
действия, видимый фокус, роли и доступные имена у кнопок раскрытия и фильтров, статус и
severity читаются текстом, а не только цветом. Автоматическая проверка (`axe`) ловит часть
и включается в те же тесты; остальное — чек-лист в ревью.

### 3.8 Производительность [целевое]

Дифф на 5000 строк и 200 файлов: время до первого отображения, отсутствие зависания при
раскрытии контекста, поведение прокрутки. Если порог не держится — это требование к
виртуализации списка строк, а не повод ослабить порог.

## 4. Тестовые данные

| Класс | Как устроен |
|---|---|
| Фикстуры диффа | один набор на репозиторий, в `src/test/fixtures`: маленький дифф, многофайловый, только удаления, переименование, бинарный, дифф на 5000 строк |
| Фабрики моделей | `ReviewRun`, `DiffFile`, `DiffHunk`, `DiffLine`, `ReviewComment` с фиксированными идентификаторами и временем — аргументами, а не из `Date.now()` |
| Mock adapter | реализует границу данных; тест подменяет его, а не `fetch` |

Фикстуры не содержат чужого кода и персональных данных: содержимое диффов синтетическое.
Время и идентификаторы фиксированы, иначе тест начинает падать по календарю.

## 5. Гейты

**Мёрж PR:** `typecheck`, `lint`, `stylelint`, `format:check` зелёные; `pnpm run test`
проходит целиком; у нового компонента есть тест на отображение и на действие пользователя;
у нового запроса данных закрыты четыре состояния; покрытие не ниже порога.

Порог покрытия задаётся в `vite.config.ts` (`test.coverage.thresholds`) и проверяется CI —
иначе «покрытие не упало» некому измерить. Стартовое значение — 70 % строк, для чистой
логики в `shared` и `entities` — 90 %: там нет причин для непокрытой ветки. Порог
повышается по мере роста кода и не опускается без записанного решения в PR.

Не проходит ревью, даже если тесты зелёные: селектор по классу или имени компонента,
снапшот без утверждения, тавтологический тест, мок `fetch` вместо подмены адаптера.

**Релиз:** интеграционные INT-01…INT-06 проходят; дымовой E2E зелёный; проверка
доступности без нарушений на основных экранах; дифф на 5000 строк укладывается в порог.

CI сегодня гоняет `typecheck`, `lint` и `test` — тремя джобами. К ним добавляются
`stylelint`, `format:check` (команды есть, в CI не включены) и сбор покрытия. Важно:
`format:check` сейчас падает и на `develop`, поэтому включать его в блокирующий гейт
можно только после разовой чистки форматирования — иначе первый же PR встанет из-за чужих
файлов. Отдельными джобами, а не шагами одной: совмещённая сообщает один провал на две
несвязанные причины.

## 6. Шаблон тест-кейса

```
ID:              <УРОВЕНЬ>-<номер>        UNIT-007, INT-03, E2E-02
Уровень:         Unit | Компонентный | Фичевый | Интеграционный | Контрактный | E2E
Риск:            R-1 … R-5
Предусловия:     данные адаптера, состояние стора, размер окна
Шаги:            1. … 2. …
Ожидание:        что видит и может сделать пользователь
Не ожидается:    дубль комментария, потеря раскрытого контекста, белый экран
Автоматизирован: путь к тесту | нет + причина
```

Ответственность: разработчик — unit и компонентные тесты на свой код; QA — интеграционные,
контрактные, E2E и доступность; DevOps — джобы CI. План правится в том же PR, что меняет
описанное поведение.
