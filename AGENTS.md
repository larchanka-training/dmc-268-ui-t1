# AGENTS.md

Фронтенд сервиса AI code review: интерфейс просмотра прогона ревью — статус, изменения в коде,
контекст вокруг них и inline-замечания. Бэкенд — репозиторий `dmc-268-api-t1`.

Перед тем как писать код, прочитайте [`.agents/rules/frontend.md`](.agents/rules/frontend.md) —
команды, слои, состояние и тесты. Перед работой с ветками, задачами и пул-реквестами —
[`.agents/rules/git-and-pr.md`](.agents/rules/git-and-pr.md).

## Правила, которые нельзя нарушать

Они здесь целиком, а не ссылкой: ссылку агент может не открыть.

- Зависимости ставим и обновляем **только через `pnpm`**: `pnpm install --frozen-lockfile`.
  Ни `npm`, ни `yarn` — lock-файл в репозитории один.
- Node 24, версия зафиксирована в `.nvmrc`.
- Проверки перед коммитом: `pnpm run typecheck`, `pnpm run lint`, `pnpm run stylelint`,
  `pnpm run format:check`, `pnpm run test`, `pnpm api:check`.
- **Импорт только вниз по слоям** Feature-Sliced Design: `app` → `pages` → `widgets` →
  `features` → `entities` → `shared`. Внутрь чужого слайса в обход его `index.ts` не ходим.
- **Серверные данные живут в TanStack Query**, состояние интерфейса — в Zustand, состояние
  одного компонента — в `useState`. Серверные данные не дублируются в store.
- `any` не используем; данные с границы приходят как `unknown` и валидируются.
- **Типы API — из контракта бэкенда**: `src/shared/api/contract/schema.d.ts` генерируется
  `pnpm api:sync` из `docs/openapi/openapi.json` репозитория `dmc-268-api-t1` на коммите из
  `src/shared/api/contract/VERSION`; контракт бэкенд строит из кода FastAPI. Тип ответа ручки,
  описанной в контракте, руками не пишется, сгенерированные файлы руками не правятся. Нужно
  поле или ручка, которой в контракте нет, — сначала PR в бэкенд с роутом (запланированная
  ручка — заглушка с `501 NOT_IMPLEMENTED`), потом `pnpm api:sync`. Фиксируется только коммит из `develop` бэкенда: коммит из PR бэкенда
  (`pnpm api:sync <sha>`) — временно, пока фронт в работе, CI не пропустит его в мёрж. Моки
  отвечают по типам контракта. Расхождение ловит `pnpm api:check`.
- Поведение меняется **только через OpenSpec-change**. Каталог `openspec/specs/` руками в обход
  change не правится.
- Работаем по git flow: ветка от `develop`, пул-реквест в `develop`, в `main` только то, что
  прошло `develop`.
- Имена веток: `feat/…`, `fix/…`, `deps-update-YYYY-MM-DD`. Коммиты — conventional commits.
  У пул-реквеста обязательны осмысленный заголовок и описание: это первый контекст для
  ревью-бота.
- Пул-реквест **всегда привязан к своей задаче**: `Closes #N` в своём репозитории, панель
  Development — в чужом.
- Задача, которую надо делать в обоих репозиториях, заводится **родительским issue и двумя
  sub-issues** `— backend` и `— frontend`; родитель закрывается последним.
- Замечание с ревью закрываем **в его треде**, и резолвит тот, чьё требование выполнено: правку
  — мы, вопрос — задавший, спор — автор замечания. Молча резолвить нельзя. После пачки правок —
  один перезапрос ревью.
- Всё, что делается на GitHub, делаем **через `gh`**; нет подкоманды — `gh api` или
  `gh api graphql`; веб последним.
- Пишем **по-русски всё**: документацию, комментарии, тексты задач, описания пул-реквестов,
  ответы в тредах, артефакты OpenSpec. Английскими остаются имена в коде, команды, названия
  инструментов и термины без устоявшегося русского эквивалента.
