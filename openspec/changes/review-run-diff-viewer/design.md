## Context

Экран строится до появления API ревью. Модели — `FRONTEND_ARCHITECTURE.md` ревизии 6.1, §4: `ReviewRun`, `ReviewFinding`, `PublishedComment` повторяют доменные значения бэкенда; `DiffFileSummary`, `DiffFile`, `DiffHunk`, `DiffLine` и `ReviewRunAction` — UI mock-модели. Задача спринта местами шире модели: в ней severity Critical / Warning / Info и «автор, ветки, скор/вердикт» в метаданных.

## Goals / Non-Goals

**Goals:**

- Дифф выбранного файла в двух режимах, с подсветкой синтаксиса и номерами строк обеих сторон.
- Замечание AI появляется под строкой своей стороны (`old` или `new`), а не рядом с «примерно той» строкой.
- Свёрнутый контекст раскрывается без отдельного компонента и нового формата данных (FE-DEC-05).
- Некорректные данные adapter не доходят до компонентов.
- Экран переживает незнакомый статус прогона.

**Non-Goals:**

- Собственная реализация диффа и подсветки.
- Маршруты, HTTP-клиент, polling, авторизация — вне scope архитектуры (§1.3).

## Decisions

### Дифф: `@git-diff-view/react`

Рассмотрены популярные библиотеки. `react-diff-viewer-continued` (~1 млн загрузок в неделю) не умеет вставлять виджеты под строкой — inline-замечания в нём не сделать. `react-diff-view` (~320 тыс.) умеет, но подсветка в нём совместима только с `refractor@3`, который тянет устаревший `prismjs` с известной уязвимостью. `@git-diff-view/react` (~100 тыс., активно поддерживается) даёт split и unified, подсветку из коробки и `extendData` — данные по номеру строки отдельно для старой и новой стороны, ровно в форме `ReviewFinding.side` + `old_line`/`new_line`.

Библиотека принимает текст unified-диффа, поэтому `entities/diff` переводит структурный `DiffFile` в текст (`toUnifiedDiff`). `DiffHunk` и `DiffLine` из §5.2 остаются моделями; как React-компоненты их роль выполняет библиотека, а `ReviewCommentThread` рендерится в её виджете под строкой.

### Свёрнутый контекст

`collapseContext` прячет строки с `is_collapsed_context`, которых нет в `expanded_context_line_ids`, и делит hunk со скрытым блоком посередине на два с пересчитанными заголовками `@@` — номера строк остаются верными. Кнопка раскрытия стоит в виджете под последней видимой строкой перед блоком (или под первой после него, если блок открывает hunk) — на новой стороне, а если у этой строки есть только старая сторона (удаление), то на старой: блок между удалениями без кнопки не остаётся. Раскрытие добавляет идентификаторы строк блока в стор, поэтому один блок не раскрывает другой hunk. Строка, к которой привязано замечание, в свёрнутом блоке не прячется. Если в куске после свёртки нет строк одной из сторон, её начало в `@@` — номер последней строки этой стороны перед куском с учётом скрытых, как в unified-диффе, а не начало исходного hunk.

### Граница данных — adapter, а не `fetch`

`shared/api` задаёт `ApiTransport { get(path): Promise<unknown> }`. `pages/review-run/model/mockReview` запрашивает `MockReviewState` одним запросом `['mock-review']` и валидирует его Zod-схемой, собранной из схем сущностей. Mock adapter и будущий HTTP-клиент реализуют один интерфейс; тесты подменяют adapter.

### Композиция экрана в `pages`

`ReviewRunView` содержит `ReviewWorkspace` и `RunInspector` — соседние виджеты, а FSD запрещает импорт внутри слоя, поэтому композиция обязана жить слоем выше. Ревизия 5.0 такого слоя не предусматривала, и экран временно собирался в `app`; ревизия 6.0 завела `pages/review-run` (§3) и прямо говорит: «`ReviewRunView` находится в `pages`, не в `app`». Сейчас так и сделано: `widgets/review-run-view` отдаёт `RunHeader` и `ReviewSummary`, `pages/review-run` владеет запросом экрана и композицией, `app` остаётся корнем приложения с провайдерами и mock adapter.

### Статус прогона — строка, а не закрытый enum

Схема принимает любую строку в `status`. Известные значения получают подпись, незнакомое показывается как есть и считается нетерминальным. Остальные enum'ы (`side`, `severity`, `category`) строгие.

### Расширения модели ради ТЗ

ТЗ требует в шапке автора, ветки и общий скор/вердикт, а в `ReviewRun` архитектуры их нет. Моки расширяют модель полями — это предложение бэкенду, а не согласованный контракт:

```ts
merge_request: { title: string; author: string; source_branch: string; target_branch: string } | null
verdict: 'approve' | 'comment' | 'request_changes' | null // null, пока прогон не завершён
score: number | null // 0–100
change_request: { provider: string; url: string } | null
```

Автор и ветки есть в доменной `MergeRequest` бэкенда. Вердикт и оценку считает бэкенд — фронтенд не выводит итог ревью из числа замечаний сам.

### Схема прогона и ответ `GET /api/v1/reviews/{id}`

В `develop` бэкенда уже есть `GET /api/v1/reviews/{id}` (dmc-268-api-t1#36). Его `ReviewRunResponse` не отдаёт `last_progress_at`, `rejected_findings` и расширения ТЗ. Схема не должна уронить экран в `ContractError`, когда mock adapter сменится HTTP-клиентом, поэтому:

- `last_progress_at` убран: UI его не использует;
- `rejected_findings`, `merge_request`, `verdict`, `score` и `change_request` необязательны — отсутствие поля равно `null`, а UI показывает прочерк или прячет блок. Нужен ли `rejected_findings` в ответе бэкенда, решается в #18.

Тест схемы проверяет именно форму `ReviewRunResponse`. Находки бэкенд кладёт внутрь прогона — это переложит в `MockReviewState` будущий HTTP-adapter, схема сущности от этого не меняется.

### Ant Design и Tailwind: слои стилей

Ant Design — единственный UI-kit (§2 архитектуры), Tailwind задаёт раскладку и отступы, в том числе на компонентах antd. Стили antd по умолчанию идут без `@layer`, а утилиты Tailwind лежат в `@layer utilities`, и стили вне слоёв перебивают их при любой специфичности. Поэтому приложение обёрнуто в `<StyleProvider layer>` из `@ant-design/cssinjs` — стили antd попадают в слой `antd`, — а `index.css` объявляет порядок `@layer theme, base, antd, components, utilities;` до импорта Tailwind.

### Ссылка на источник без привязки к провайдеру

В интерфейсе нет названий провайдеров, ссылка подписана «Открыть источник». `provider` — любая строка. В `href` попадает только `http(s)`-адрес: `javascript:` и другие схемы отбрасываются.

### Размер бандла

Подсветка из `@git-diff-view/core` статически подключает все языки highlight.js. `DiffViewer` загружается через `React.lazy`: шапка и сводка не ждут просмотрщик.

## Risks / Trade-offs

- `@git-diff-view` моложе альтернатив и менее популярен → обёрнут в один компонент `DiffViewer`, замена затронет только его.
- Сбой библиотеки на неожиданном диффе → `DiffViewer` обёрнут в `ErrorBoundary`, падает только блок файла.
- Композиция `ReviewRunView` вне `widgets` → закрыто ревизией 6.0 архитектуры: экран переехал в `pages/review-run`.
