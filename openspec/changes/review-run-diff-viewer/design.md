## Context

Экран строится до появления API ревью. Контракт — `FRONTEND_ARCHITECTURE.md` §8.2 и §9: `ReviewRun`, `ReviewFinding`, `PublishedComment`, `DiffFileSummary`, `DiffFile`, `DiffHunk`, `DiffLine`, пути без префикса версии. Задача спринта местами шире контракта: в ней severity Critical / Warning / Info и «автор, ветки, скор/вердикт» в метаданных. Severity оставлены по контракту; автор, ветки, вердикт и оценка добавлены в DTO прогона как предложение фронтенда (см. решение ниже).

## Goals / Non-Goals

**Goals:**

- Дифф выбранного файла в двух режимах, с подсветкой синтаксиса и номерами строк обеих сторон.
- Замечание AI появляется под строкой своей стороны (`old` или `new`), а не рядом с «примерно той» строкой.
- Некорректный ответ API не доходит до компонентов.
- Экран переживает незнакомый статус прогона.

**Non-Goals:**

- Собственная реализация диффа и подсветки.
- Реальный HTTP-клиент и авторизация.
- Воспроизведение диффа на клиенте — он приходит готовым snapshot'ом по паре `base_sha`/`head_sha`.

## Decisions

### Дифф: `@git-diff-view/react`, а не собственные `DiffHunk`/`DiffLine`

Рассмотрены популярные библиотеки. `react-diff-viewer-continued` (~1 млн загрузок в неделю) не умеет вставлять виджеты под строкой — inline-замечания в нём не сделать. `react-diff-view` (~320 тыс.) умеет, но подсветка в нём совместима только с `refractor@3`, который тянет устаревший `prismjs` с известной уязвимостью. `@git-diff-view/react` (~100 тыс., активно поддерживается) даёт split и unified, подсветку из коробки и `extendData` — данные по номеру строки отдельно для старой и новой стороны, ровно в форме `ReviewFinding.side` + `old_line`/`new_line`.

Библиотека принимает текст unified-диффа, поэтому `entities/diff` переводит структурный `DiffFile` в текст (`toUnifiedDiff`). Компоненты `DiffHunk` и `DiffLine` из §5.1 архитектуры как React-компоненты не появляются: их роль выполняет библиотека, модели остаются.

### Граница данных — транспорт, а не `fetch`

`shared/api` задаёт `ApiTransport { get(path): Promise<unknown> }`. Entity API валидирует ответ Zod-схемой (`parseResponse`) и только потом отдаёт его в query hook. Mock adapter и будущий HTTP-клиент реализуют один интерфейс; тесты подменяют транспорт.

### Статус прогона — строка, а не закрытый enum

Схема принимает любую строку в `status`. Известные значения получают подпись, незнакомое показывается как есть и считается нетерминальным — прогон продолжает опрашиваться. Остальные enum'ы (`side`, `severity`, `category`) строгие по §9.2.

### Состояние

| Данные                               | Владелец                                 |
| ------------------------------------ | ---------------------------------------- |
| прогон, файлы, дифф файла, замечания | TanStack Query, ключи из §8.1            |
| выбранный файл, режим диффа          | Zustand-стор виджета `review-workspace`  |
| раскрыта ли карточка                 | Headless UI `Disclosure` внутри карточки |

Режим диффа живёт в сторе, а не в `DiffViewer`: иначе он сбрасывался бы при смене файла (замечание к PR #6).

### Автор, ветки, вердикт и оценка — расширение DTO прогона

ТЗ требует в шапке автора, ветки и общий скор/вердикт, а в `ReviewRun` из §8.2 их нет. Моки расширяют DTO тремя полями — это предложение бэкенду, а не согласованный контракт:

```ts
merge_request: { title: string; author: string; source_branch: string; target_branch: string } | null
verdict: 'approve' | 'comment' | 'request_changes' | null // null, пока прогон не завершён
score: number | null // 0–100
```

`merge_request` отдаётся вместе с прогоном, а не отдельным запросом: шапке он нужен сразу. Вердикт и оценку считает бэкенд — фронтенд не выводит итог ревью из числа замечаний сам, иначе правило оценки окажется в двух местах.

### Ссылка на источник без привязки к провайдеру

Продукт общий, а не надстройка над одним Git-хостингом: в интерфейсе нет названий провайдеров, ссылка подписана «Открыть источник». `ChangeRequestLink.provider` принимается как любая строка — адрес собирает бэкенд, UI его не разбирает. В `href` попадает только `http(s)`-адрес: `javascript:` и другие схемы отбрасываются.

### Polling

Прогон опрашивается раз в 3 секунды, пока статус нетерминальный. Замечания опрашиваются вместе с ним — они появляются по ходу публикации, — и после перехода в терминальный статус запрашиваются ещё раз.

### Привязка замечаний

Замечание без номера строки на своей стороне показывается в сводке («Без привязки к строке»). Замечание со строкой, которой нет в показанных hunk'ах, выводится над диффом файла, а не теряется молча. Счётчик замечаний в списке файлов считается из тех же данных, что и карточки.

### Размер бандла

Подсветка из `@git-diff-view/core` статически подключает все языки highlight.js. `DiffViewer` загружается через `React.lazy`: заголовок и сводка не ждут просмотрщик (основной чанк ~150 КБ gzip, просмотрщик ~340 КБ gzip).

## Risks / Trade-offs

- `@git-diff-view` моложе альтернатив и менее популярен → обёрнут в один компонент `DiffViewer`, замена затронет только его.
- Сбой библиотеки на неожиданном диффе → `DiffViewer` обёрнут в `ErrorBoundary`, падает только блок файла.
- Форма ответа `/findings` не согласована с бэкендом → зафиксирована в `FindingsResponseSchema`, расхождение поймает Zod.

## Open Questions

- Severity в задаче (Critical / Warning / Info) против контракта (`low | medium | high | critical`). Сейчас по контракту.
- Поля `merge_request`, `verdict`, `score`: согласовать с бэкендом имена, форму и правило расчёта оценки.
- Поведение на `401` во время polling'а — зона Инженера 1, в этой работе не определено.
