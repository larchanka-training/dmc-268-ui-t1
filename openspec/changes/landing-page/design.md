## Context

Интерфейс — SPA на Vite 8, React 19, Tailwind 4 и Ant Design. Собирается при сборке образа и отдаётся nginx (`nginx/site.conf`). Сейчас любой путь, кроме `/api/` и существующих файлов, получает `index.html` приложения (`try_files $uri $uri/ /index.html`). Кабинет из #16 (уже в `develop`) держит маршруты `react-router-dom` от корня: `/`, `/login`, `/oauth/callback`, `/repositories`, `/reviews/{id}`.

Стенд открывается по IP с сертификатом Let's Encrypt. Проект учебный, поэтому позиции в поисковой выдаче не цель. Готовый HTML и метаданные нужны, чтобы страница была понятна без JS, правильно показывалась в превью ссылок и проходила аудит Lighthouse.

## Goals / Non-Goals

**Goals:**

- `/` отдаёт готовый HTML лендинга с текстом и метаданными, без JS приложения.
- Приложение и лендинг не делят пространство адресов: новый маршрут кабинета не требует правок nginx, а новая статичная страница не требует правок роутера.
- Лендинг получает HTTP/2, HTTP/3, gzip и кэш-заголовки от той же доставки, без второго сервера.

**Non-Goals:**

- Второй стек вроде Astro или Next ради одной страницы.
- SSR приложения: кабинет и экран прогона остаются SPA за входом, индексировать их незачем.
- Свой домен и работа над позициями в выдаче.
- Блог, документация, мультиязычность.

## Decisions

### Два пространства адресов: `/app/*` и статика

| Путь                                             | Что отдаётся                                                                                              |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| `/app`, `/app/…`                                 | HTML приложения (`/app/index.html`) для любого пути под префиксом; `/app` без слеша — редирект на `/app/` |
| `/login`                                         | статичная страница входа; с cookie сессии — редирект на `/app/`                                           |
| `/assets/…`                                      | файлы сборки с хэшем в имени, общие для лендинга и приложения                                             |
| `/api/…`                                         | прокси на API, как сейчас                                                                                 |
| `/`, `/robots.txt`, `/sitemap.xml`, другие файлы | статика из `dist`                                                                                         |
| остальное                                        | `404` со статичной `404.html`                                                                             |

Префикс у приложения, а не у лендинга: все маршруты SPA попадают под одно правило nginx, и nginx не нужно знать список маршрутов. Без префикса пришлось бы отдавать fallback на всё, кроме `/`, и опечатка в ссылке на лендинг открывала бы приложение.

`/assets/` остаётся общим, а не переезжает в `/app/assets/`: у лендинга свой CSS, и правило `immutable` на год уже работает для обоих.

### Лендинг — вторая точка входа в Vite

В `build.rolldownOptions.input` две страницы: `index.html` — лендинг, `app/index.html` — приложение. Vite собирает их за один проход, общий код не дублируется, хэши и `.gz` получают обе страницы. `404.html` — третья точка входа.

Лендинг — HTML с классами Tailwind и своим CSS-входом `src/landing/landing.css`. React и Ant Design в него не попадают. Если понадобится переиспользовать компоненты, следующий шаг — пререндер при сборке через `renderToStaticMarkup`, а не SSR.

`lang="ru"`, один `<h1>`, разделы с `<h2>`, у картинок `alt`, `width` и `height`. Скриншоты — WebP в `public/landing/`, снятые с экрана на моках.

### Вход — статика, OAuth — на бэкенде

На лендинге одна кнопка «Войти», она всегда ведёт на `/login`. Лендинг не выясняет, вошёл ли пользователь: без JS это невозможно, а встроенный скрипт или второй вариант страницы ради одной надписи не окупаются.

`/login` — статичная страница с двумя ссылками: `/api/v1/auth/github/login` и `/api/v1/auth/gitlab/login`. Дальше всё делает бэкенд: уводит к провайдеру, принимает callback под `/api/`, ставит httpOnly cookie сессии и перенаправляет на `/app/`. В SPA не остаётся ни экрана входа, ни callback, ни хранения токенов; `RequireAuth` при `401` уводит на `/login?redirect=<текущий путь>`.

Вошедшему страница входа не нужна: `location = /login` при наличии cookie сессии отвечает `302` на `/app/`. nginx проверяет наличие cookie, а не её действительность — без запроса к API. Петлю при протухшей cookie снимает бэкенд: ответ `401` удаляет cookie, и следующий заход на `/login` уже без неё.

От бэкенда нужно: имя cookie сессии (в конфиге — `session`), удаление cookie в ответе `401` и эндпоинты `/api/v1/auth/{provider}/login` и callback.

### Dev-сервер

Vite в режиме `spa` отдаёт на неизвестный путь корневой `index.html`, то есть лендинг. Поэтому `appType: 'mpa'` и небольшой плагин, который переписывает `/app` и `/app/*` без расширения файла на `/app/index.html`. Правило переписывания — чистая функция с тестом, тем же правилом, что и в nginx.

### Абсолютный адрес — при сборке образа

Canonical, `og:url`, `og:image` и `sitemap.xml` требуют абсолютный адрес, а статика собирается до деплоя. Адрес стенда передаётся в сборку аргументом `PUBLIC_ORIGIN`: Vite подставляет его в HTML через `transformIndexHtml`, а плагин сборки пишет `sitemap.xml`. Без аргумента берётся `http://localhost:3000`. Стенд один, поэтому образ собирается под его адрес: `vars.VPS_DMC268_IP_T1` уже доступен job'у сборки.

Подстановка при старте контейнера, как у `https.conf.template`, не подходит: рядом лежат готовые `.gz`, и правка HTML разошлась бы с ними.

`robots.txt` разрешает `/`, закрывает `/app/` и `/api/` и указывает `Sitemap`.

### Кэш

Лендинг, `404.html` и `/app/index.html` — `no-cache`, как сейчас `index.html`: это документы, с которых начинается загрузка, и требование «браузер получает новую версию» распространяется на все три.

### Гость не попадает в `/app/`

`location /app/` и `location = /app` без cookie сессии отвечают `302` на `/login?redirect=<путь>`. Гость не скачивает HTML и бандл приложения и не делает запрос к API, чтобы узнать, что он не вошёл. Вместе с редиректом с `/login` для вошедшего защита симметрична.

nginx проверяет наличие cookie, а не действительность. С протухшей cookie пользователь попадает в приложение, первый запрос к API возвращает `401` и удаляет cookie, `RequireAuth` уводит на `/login?redirect=<текущий путь>` — и nginx уже показывает страницу входа. Поэтому `RequireAuth` в приложении остаётся. Тот же путь закрывает сессию, истёкшую посреди работы: после входа пользователь возвращается на экран, где был.

Путь берётся из `$request_uri` без строки запроса: параметры вроде фильтров при возврате теряются. Кодировать их стандартный nginx не умеет; если понадобится, `redirect` переедет в короткоживущую cookie. `$uri` не годится: он раскодирован, и `%0D%0A` в адресе стал бы переводом строки в `Location` — чужим заголовком в ответе; проверено на образе. Путь с символами вне `[-A-Za-z0-9/_.~%]` заменяется на `/app/`. Вычисление стоит на уровне `server`: `set` внутри `if` в `location` переключает запрос на конфигурацию `if` без `try_files`.

### `redirect` и ошибка на странице входа

Статичная страница не может без JS ни дописать `redirect` к ссылкам входа, ни показать текст ошибки из `?error=`. Для этого — небольшой модуль `src/landing/login.ts`: модули выполняются после разбора страницы и отрисовку не блокируют, а страница меняется только при наличии параметров. Сообщения для кодов `denied`, `state_mismatch`, `provider_unavailable` и общее для незнакомого кода свёрстаны в HTML и скрыты, скрипт показывает нужное. Код в селектор не подставляется, а сравнивается с атрибутом. Без JS вход работает, теряются только возврат на исходную страницу и текст ошибки.

`redirect` скрипт передаёт как есть: проверяет его бэкенд (change `auth-session`, api#47).

### Кабинет под `/app`

`<BrowserRouter basename="/app">`: маршруты кабинета внутри не меняются, адреса — `/app/`, `/app/repositories`, `/app/reviews/{id}`. Экран входа и `/oauth/callback` из SPA уходят: вход — статика `/login`, callback — на бэкенде.

Отдельные правила nginx нужны только адресам без файла в `dist`, которые не под `/app/`. Статичные файлы nginx находит сам через `try_files`. `/login` — единственное исключение: адрес без `.html` и с редиректом для вошедшего. Тот же адрес для dev-сервера — `STATIC_PAGES` в `src/build/appRoutes.ts`.

### Проверки

- Job `nginx` в CI, кроме `nginx -t`, поднимает образ в режиме HTTP и проверяет: `/` отдаёт лендинг с `<meta name="description">` и без `<div id="root">`; `/app/` и `/app/reviews/123` отдают приложение; `/nope` — `404` со статичной страницей; `/app/index.html` и `/` — `no-cache`.
- `deploy.yml`: проверка gzip берёт бандл из `/app/`, а не из `/`; те же проверки маршрутизации — на стенде по HTTPS.
- Lighthouse для лендинга, SEO и Accessibility не ниже 90 — вручную перед мерджем, результат в описании PR.

## Risks / Trade-offs

- **Старые ссылки на `/reviews/…`** после переезда получат 404. → Ссылок наружу пока нет, стенд не в проде. Если появятся до мерджа — `location` с редиректом на `/app/…`.
- **Образ привязан к адресу стенда.** → Стенд один; для второго окружения адрес — аргумент сборки, не код.
- **Скриншоты устаревают** вместе с интерфейсом. → Снимаются с моков одной командой, вместе с изменением экранов.
