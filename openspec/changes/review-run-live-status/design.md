## Context

Экран `ReviewRunView` (change `review-run-diff-viewer`, PR #19) получает прогон одним запросом и дальше не обновляется. Статусы прогона — `ReviewRunStatus` бэкенда: `queued`, `building_context`, `analysing`, `publishing`, `completed`, `failed`, `cancelled`. Терминальные — последние три. Worker пишет статус и `last_progress_at` в базу (`app/domain/lifecycle.py`). API и worker — разные процессы, поэтому события до браузера доставляет API.

Сессия хранится в httpOnly cookie (#17), запросы идут с `credentials: 'include'`, API — на том же origin за nginx (`location /api/`).

## Goals / Non-Goals

**Goals:**

- Статус открытого прогона меняется на экране без перезагрузки, с задержкой не больше пары секунд после записи в базу.
- Обрыв соединения не теряет переходы и не оставляет на экране устаревший статус после переподключения.
- Пользователь видит, на каком этапе прогон, и где он упал.
- Замечания фильтруются по файлу, severity и тексту, фильтры не сбрасываются при обновлении прогона.

**Non-Goals:**

- WebSocket: обратного канала от фронтенда к бэкенду нет.
- Polling — ни основным, ни запасным механизмом.
- Поток замечаний по одному по мере их появления: замечания приходят одним перезапросом после завершения.
- Реализация эндпоинта на бэкенде.

## Decisions

### Транспорт: SSE, без polling

Фронтенду нужны только уведомления от сервера, и SSE даёт ровно это поверх обычного HTTP: проходит через тот же nginx, ту же cookie и тот же префикс `/api/v1`. WebSocket добавил бы upgrade в прокси и собственный протокол сообщений без пользы.

Polling не нужен, потому что сервер начинает каждый поток со снимка текущего статуса (см. контракт ниже). `EventSource` переподключается сам, и после переподключения клиент получает актуальное состояние, а не догоняет пропущенные события. Поэтому `Last-Event-ID` и повтор истории тоже не нужны.

### Клиент: нативный `EventSource`

`new EventSource(url, { withCredentials: true })`. Заголовки ставить не надо: авторизация — cookie, origin тот же. `@microsoft/fetch-event-source` и подобные библиотеки нужны для `Authorization`-заголовка или POST, у нас нет ни того, ни другого.

`EventSource` закрывается за интерфейсом в `shared/api`, рядом с `ApiTransport`:

```ts
type EventStream = {
  subscribe(
    path: string,
    handlers: {
      onEvent: (type: string, data: unknown) => void
      onStateChange: (state: StreamState) => void
    },
  ): () => void // отписка
}

type StreamState = 'connecting' | 'open' | 'reconnecting' | 'failed'
```

Реализаций две: на `EventSource` и mock для `app/mocks` и тестов. Mock проигрывает сценарий статусов по таймеру, тест управляет им вручную.

### Контракт событий — предложение бэкенду

```
GET /api/v1/reviews/{review_run_id}/events
Accept: text/event-stream

200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no

retry: 3000

event: status
data: {"review_run_id":"…","status":"analysing","last_progress_at":"2026-10-11T10:00:00Z","failed_stage":null,"failure_reason":null}

event: ping
data: {}
```

- `404` до начала потока, если прогона нет. Без сессии — `401`.
- Первое событие `status` после подключения — снимок текущего состояния. Дальше — по событию на каждую смену статуса.
- После терминального статуса сервер отправляет его и закрывает поток.
- Событие `ping` после 14 секунд тишины. Оно держит соединение живым: nginx по умолчанию рвёт прокси-соединение после 60 секунд тишины (`proxy_read_timeout`), NAT и балансировщики по пути забывают молчащее соединение. Именно событие, а не SSE-комментарий `: ping`: комментарии `EventSource` в JS не отдаёт, и клиент не отличил бы тихий поток от мёртвого.
- `X-Accel-Buffering: no` отключает буферизацию в nginx для этого ответа, и отдельный `location` во фронтовом nginx не нужен.
- `failed_stage` — статус, на котором прогон упал (`building_context` | `analysing` | `publishing`), или `null`. Бэкенд хранит его в прогоне и отдаёт и в событии, и в `GET /api/v1/reviews/{id}` (api#56); для сбоя из `queued` — `null`.

Для данных хватает одного типа события `status`: снимок и изменение несут одну форму; `ping` данных не несёт. Как API узнаёт об изменениях — опрос базы внутри эндпоинта, Redis pub/sub или `LISTEN/NOTIFY` — решает бэкенд, на контракт это не влияет.

Событие проверяется Zod-схемой `RunStatusEventSchema` в `entities/review-run`. `status` — любая строка, как в `ReviewRunSchema`. Событие вне схемы отбрасывается и пишется в консоль как `ContractError`; экран не падает и подписку не рвёт.

### Подписка и кэш

`features/live-run-status` даёт `useRunLiveStatus(runId)`:

- подписывается, только пока прогон в кэше нетерминальный;
- на событие патчит в кэше TanStack Query `status`, `last_progress_at`, `failed_stage`, `failure_reason`, не трогая остальное;
- при первом терминальном статусе один раз инвалидирует запрос прогона — так приходят замечания, вердикт, длительность и токены — и отписывается;
- закрывает поток, когда вкладка скрыта (`visibilitychange`), и открывает снова, когда она видна: снимок при подключении возвращает актуальное состояние. Так фоновые вкладки не держат соединения.

Экран открывается по `/reviews/:reviewId` и грузит прогон с этим id; ключ кэша — по id, поэтому прогоны в разных вкладках и переходы между ними не смешиваются. Ключ держится в `useMemo`: он в зависимостях эффекта подписки, и новый массив на каждый рендер переоткрывал бы поток.

Источник правды для экрана по-прежнему кэш запроса прогона. События — способ его обновить, а не второе состояние.

### Состояние соединения

| `StreamState`  | Что видит пользователь                                                           |
| -------------- | -------------------------------------------------------------------------------- |
| `connecting`   | ничего лишнего, показан статус из кэша                                           |
| `open`         | ничего лишнего                                                                   |
| `reconnecting` | через 5 секунд — плашка «Соединение потеряно, переподключаемся», данные остаются |
| `failed`       | «Не удалось получить обновления статуса» и кнопка «Обновить»                     |

`failed` — когда `EventSource` перешёл в `CLOSED` сам: сервер ответил не `text/event-stream`, например `404` или `401`. «Обновить» один раз перезапрашивает прогон и открывает подписку заново. Это действие пользователя, а не polling.

`EventSource` не отдаёт статус ответа и не отличает `401` от прочих ошибок открытия, поэтому поток при истёкшей сессии тоже показывает «Обновить», а не уводит на вход. Увод на `/login` при `401` делает `apiFetch` (появляется в ui#30: `401` → `/login?redirect=…`). После перебазирования на ui#30 экран в состоянии `failed` проверит сессию запросом через `apiFetch` (например, `/auth/me`): при истёкшей сессии `401` уведёт на вход, при живой останется «Обновить».

### Таймаут heartbeat

`EventSource` сам не замечает тихо умершее соединение: при полуоткрытом TCP, сброшенной записи NAT или смене сети браузер может минутами держать `readyState = OPEN` без единого байта. Поэтому клиент считает живым только поток, в котором приходят события. Если за `SILENCE_LIMIT` = 45 секунд (три пропущенных `ping`) не пришло ни одного события — ни `status`, ни `ping`, — клиент закрывает `EventSource`, переходит в `reconnecting` и открывает новый. Первое событие нового потока — снимок, поэтому пропущенное за время тишины не теряется. Таймер живёт в реализации `EventStream` на `EventSource`, а не в хуке: mock-источнику и тестам он не мешает.

### Пошаговый прогресс

`RunProgress` в `widgets/review-run-view` — `Steps` из Ant Design с тремя шагами.

| Статус             | Сбор контекста                              | Анализ LLM | Публикация | Подпись      |
| ------------------ | ------------------------------------------- | ---------- | ---------- | ------------ |
| `queued`           | wait                                        | wait       | wait       | «В очереди»  |
| `building_context` | process                                     | wait       | wait       |              |
| `analysing`        | finish                                      | process    | wait       |              |
| `publishing`       | finish                                      | finish     | process    |              |
| `completed`        | finish                                      | finish     | finish     |              |
| `failed`           | до `failed_stage` — finish, на нём — error  |            |            | причина сбоя |
| `cancelled`        | до последнего этапа — finish, дальше — wait |            |            | «Отменён»    |

Если `failed_stage` равен `null`, берётся последний этап, который экран видел в этой сессии. Если экран открыт уже после сбоя и этапа не видел, ни один шаг не помечается ошибкой, а подпись говорит «Этап сбоя неизвестен». Незнакомый статус шаги не двигает и показывается как есть, в `RunStatusBadge`.

Блок с шагами — `aria-live="polite"`: смена этапа объявляется скринридером.

### Зависший прогон

Если прогон нетерминальный и `last_progress_at` старше порога, `RunProgress` показывает предупреждение «Прогон давно не продвигался». Порог — константа `STALE_AFTER`, равная порогу бэкенда `stale_run_timeout_seconds`: 1800 секунд. `last_progress_at` приходит и в `GET /api/v1/reviews/{id}`, поэтому предупреждение работает и до первого события. Время сверяется по таймеру раз в 30 секунд, без запросов к серверу.

### Фильтры замечаний

Состояние — в сторе `features/filter-findings` рядом с `severity_filters`:

| Поле                 | Что фильтрует                                                         |
| -------------------- | --------------------------------------------------------------------- |
| `severity_filters`   | уже есть: замечания по severity                                       |
| `file_query`         | список файлов по подстроке пути, без учёта регистра                   |
| `only_with_findings` | скрывает файлы без замечаний под текущие фильтры замечаний            |
| `text_query`         | замечания по подстроке в `message` и `suggestion`, без учёта регистра |

Фильтры разных видов сочетаются через «и», severity между собой — через «или». Строки обрезаются по краям; пустая строка — фильтра нет. Поиск применяется с задержкой 200 мс после ввода. Счётчики в списке файлов считают замечания под фильтры, сводка — все, как и сейчас.

Если выбранный файл выпал из отфильтрованного списка, выбирается первый оставшийся. Если не осталось ни одного — пустое состояние с кнопкой «Сбросить фильтры». Фильтры живут в Zustand, а не в кэше запроса, поэтому обновление прогона по событию их не сбрасывает.

Поиск по тексту не подсвечивает совпадения: это отдельная задача, если понадобится.

## Risks / Trade-offs

- **Лимит соединений HTTP/1.1** — 6 на origin в браузере. Много открытых вкладок с прогонами съедят лимит. → Поток закрывается в скрытой вкладке, а стенд переходит на HTTP/2 и HTTP/3 (#21): там все потоки идут по одному соединению. HTTP/2 обязателен — на него браузер откатывается, где UDP закрыт; HTTP/3 поверх сохраняет поток при смене сети.
- **Буферизация в прокси** удерживает события до заполнения буфера. → `X-Accel-Buffering: no` от бэкенда; проверить на стенде, что событие доходит сразу.
- **Бэкенд-эндпоинта пока нет.** → Mock-источник за тем же интерфейсом; переход — замена реализации в `app`.
- **`failed_stage` бывает `null`** — у сбоя из `queued`. → Последний виденный этап и честная подпись «Этап сбоя неизвестен».
