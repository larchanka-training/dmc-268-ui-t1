# Spec Delta

## Purpose

Экран настроек репозитория в кабинете: форма настроек ревью, статус-панель `.review/rules.md`
с read-only превью распарсенных правил и ссылка «Прогоны репозитория» на вкладку «Ревью»
с фильтром по репозиторию.

## ADDED Requirements

### Requirement: Экран настроек репозитория

Интерфейс SHALL открывать настройки репозитория по адресу
`/app/repositories/:repositoryId/settings` внутри макета кабинета и SHALL давать вход на экран
действием «Настройки» у репозитория в списке подключённых. Если репозитория с таким
идентификатором нет, экран SHALL показывать сообщение «не найдено» и путь назад, а не пустую
страницу.

#### Scenario: Открытие настроек из списка

- **WHEN** пользователь нажимает «Настройки» у репозитория в списке подключённых
- **THEN** открывается экран настроек этого репозитория

#### Scenario: Прямая ссылка

- **WHEN** авторизованный пользователь открывает адрес настроек репозитория напрямую
- **THEN** экран отображается в макете кабинета с данными этого репозитория

#### Scenario: Репозиторий не найден

- **WHEN** в адресе идентификатор, которого нет в данных кабинета
- **THEN** экран показывает сообщение, что репозиторий не найден, и путь назад к списку

#### Scenario: Ссылка на прогоны

- **WHEN** экран настроек репозитория открыт
- **THEN** на нём есть ссылка на вкладку «Ревью» с фильтром по этому репозиторию

### Requirement: Форма настроек ревью

Экран SHALL показывать актуальные настройки ревью репозитория: включено ли авто-ревью, список
паттернов веток фильтра и минимальный уровень severity `min_severity` из уровней low, medium,
high, critical с подписями Low, Medium, High, Critical.

#### Scenario: Загрузка текущих значений

- **WHEN** экран настроек открылся
- **THEN** форма показывает сохранённые значения авто-ревью, фильтра веток и порога severity

#### Scenario: Черновик не переезжает к другому репозиторию

- **WHEN** у пользователя есть несохранённые правки в настройках одного репозитория и он
  открывает настройки другого
- **THEN** форма показывает сохранённые значения второго репозитория, а не черновик первого

### Requirement: Сохранение настроек ревью

Сохранение SHALL выполняться одним действием — запросом `PUT
/api/v1/repositories/{repository_id}/settings`, заменяющим настройки целиком: тело запроса —
все три поля (`auto_review_enabled`, `branch_filter`, `min_severity`). Перед отправкой фильтр
веток SHALL нормализоваться: обрезка пробелов, пустые паттерны — мимо, повторы не
сохраняются. На время сохранения форма SHALL блокироваться; несохранённые правки SHALL
оставаться в форме и SHALL NOT попадать в кэш данных до успешного сохранения.

#### Scenario: Сохранение

- **WHEN** пользователь меняет значения и сохраняет
- **THEN** экран показывает состояние сохранения
- **AND** после успеха форма и данные показывают новые значения

#### Scenario: Нормализация фильтра веток

- **WHEN** среди введённых паттернов веток есть значения с пробелами по краям, пустые и
  повторяющиеся
- **THEN** сохраняются обрезанные непустые паттерны без повторов, в исходном порядке

#### Scenario: Ошибка сохранения

- **WHEN** сохранение завершилось ошибкой
- **THEN** экран показывает ошибку и возможность повторить
- **AND** введённые значения остаются в форме

### Requirement: Сброс несохранённых правок

Явный сброс SHALL возвращать в форму последние сохранённые значения и SHALL убирать показанные
состояния сохранения — успех и ошибку.

#### Scenario: Сброс несохранённых правок

- **WHEN** пользователь сбрасывает форму
- **THEN** форма возвращается к последним сохранённым значениям
- **AND** сообщения об успехе или ошибке сохранения исчезают

### Requirement: Статус `.review/rules.md`

Экран SHALL показывать один из пяти исходов загрузки `.review/rules.md` в ветке репозитория:
правила загружены (`loaded`), файл разобран, но ни один раздел не стал правилом (`empty`),
файла нет (`absent`), файл больше лимита (`too_large`) или файл недоступен (`unavailable`).
Когда применимых правил нет, экран SHALL сообщать, что ревью идёт по стандартным критериям;
если файла нет — с предложением его создать.

#### Scenario: Правила найдены

- **WHEN** в ветке репозитория есть `.review/rules.md` с применимыми правилами
- **THEN** бейдж сообщает, что применяются кастомные правила
- **AND** показывается превью правил с веткой, из которой они взяты

#### Scenario: Файл без применимых правил

- **WHEN** файл правил разобран, но ни один раздел не стал правилом
- **THEN** бейдж сообщает, что правила не применяются
- **AND** показывается сообщение о ревью по стандартным критериям
- **AND** отклонённые разделы показываются с причинами

#### Scenario: Правил нет

- **WHEN** в ветке репозитория нет `.review/rules.md`
- **THEN** бейдж сообщает о дефолтных правилах
- **AND** показывается предупреждение с предложением создать файл

#### Scenario: Файл больше лимита

- **WHEN** `.review/rules.md` больше лимита бэкенда
- **THEN** бейдж сообщает о слишком большом файле
- **AND** показывается сообщение о ревью по стандартным критериям

#### Scenario: Файл недоступен

- **WHEN** файл правил не удалось получить из VCS
- **THEN** бейдж сообщает о недоступности правил
- **AND** показывается сообщение о ревью по стандартным критериям

### Requirement: Превью правил

Превью SHALL показывать каждое правило целиком: имя, паттерны области действия `pattern` и
`exclude`, нумерованные проверки. Разделы, отклонённые разбором, SHALL показываться с именем
и причиной отклонения. Превью SHALL NOT допускать редактирования.

#### Scenario: Правило целиком

- **WHEN** файл правил загружен
- **THEN** каждое правило показано с именем, паттернами области действия и проверками

#### Scenario: Отклонённый раздел

- **WHEN** раздел файла не стал правилом
- **THEN** превью показывает его имя и причину отклонения

#### Scenario: Превью только читается

- **WHEN** показано превью правил
- **THEN** ни одно его поле не редактируется

### Requirement: Состояния данных экрана

Каждый блок экрана — настройки, статус правил — SHALL отдельно обрабатывать загрузку
и ошибку; ошибка одного блока SHALL NOT ломать остальные. Данные SHALL приходить через серверный
слой данных по ручкам контракта (mock adapter и HTTP-клиент — одна граница) и SHALL NOT
дублироваться в глобальном сторе. Данные вне схемы SHALL показываться как ошибка контракта
в своём блоке.

#### Scenario: Ошибка одного блока

- **WHEN** сервер отдаёт ошибку для одного из блоков
- **THEN** этот блок показывает ошибку
- **AND** остальные блоки продолжают работать

#### Scenario: Данные вне схемы

- **WHEN** ответ блока не проходит валидацию схемы
- **THEN** блок показывает ошибку несоответствия контракту, а не падает

### Requirement: Предложение повтора

Повтор SHALL предлагаться только для ошибок, которые может изменить повтор, — не для клиентских
4xx.

#### Scenario: Клиентская ошибка без повтора

- **WHEN** блок получил ошибку 4xx
- **THEN** блок показывает ошибку без предложения повторить

### Requirement: Ручки блока, ещё не реализованные бэкендом

Если ручка блока отвечает `501` с кодом `NOT_IMPLEMENTED` — она описана в контракте, но
бэкенд ещё не реализовал её, — этот блок SHALL показывать сообщение вида «пока недоступно»,
SHALL NOT показывать ошибку с повтором, а остальные блоки SHALL продолжать работать со
своими данными.

#### Scenario: Блок на ручке-заглушке

- **WHEN** `GET /repositories/{id}/settings` (или `…/rules`) отвечает `501 NOT_IMPLEMENTED`
- **THEN** этот блок показывает «пока недоступно»
- **AND** остальные блоки работают как обычно

### Requirement: Фоновое обновление блоков

Ошибка фонового обновления блока при живых данных SHALL NOT заменять его содержимое: блок
продолжает показывать последние загруженные данные и сообщает ошибку с возможностью повторить.
Полная ошибка с повтором SHALL показываться только когда данных блока нет.

#### Scenario: Ошибка фонового обновления

- **WHEN** фоновое обновление данных блока завершилось ошибкой, а данные в кэше есть
- **THEN** блок продолжает показывать данные из кэша
- **AND** блок сообщает ошибку с возможностью повторить
