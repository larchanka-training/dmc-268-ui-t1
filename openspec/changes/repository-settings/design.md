# Design

## Context

Кабинет уже собран (change `cabinet-mock-oauth`, PR #16): `AppRouter` с `RequireAuth` +
`AppLayout`, плоские страницы в `src/pages`, `entities/repository` и
`features/repository/model/repositoryQueries.ts`. Ручки блока описаны контрактом `b035f3e`
(бэкенд-задача api#113 закрыта, контракт влит во фронт в PR #56): `GET
/api/v1/repositories/{repository_id}` реализована; `GET`/`PUT …/settings` и `GET …/rules` —
заглушки `501 NOT_IMPLEMENTED`. Данные идут через `ApiTransport` из `shared/api/transport.ts`
(включая метод `put`): HTTP-клиент и mock adapter — одна граница, компонент не знает, откуда
ответ. Пока ручки-заглушки отвечают 501, экран «идёт» на моках (`src/app/mocks`), а блок на 501
показывает «пока недоступно» — паттерн `ConnectRepositoryPage` и вкладки «Ревью». Парсинг
markdown-правил — задача бэкенда: ручка `GET …/rules` отдаёт уже распарсенные правила.

## Goals / Non-Goals

**Goals:**

- Два блока одного экрана — форма настроек, статус правил — за одним `ApiTransport`
  (HTTP-клиент или mock adapter) с Zod-валидацией ответа на границе.
- Модели совпадают со схемами контракта поле в поле (`auto_review_enabled`, `branch_filter`,
  `min_severity`); совпадение проверяет компилятор (`MatchesContract`).
- Превью правил без парсинга markdown во фронтенде.
- Прогоны репозитория не дублируются в настройках: ссылка «Прогоны репозитория» ведёт на
  вкладку «Ревью» с фильтром `repository_id`.

**Non-Goals:**

- Реализация ручек бэкендом и переключение стенда с моков на HTTP: экран различает 501 и
  ошибку, отдельной переделки не требует.
- Редактирование `.review/rules.md`.
- Глубокая валидация glob-паттернов фильтра веток: формат строки, семантику проверяет бэкенд.

## Decisions

### Маршрут и композиция — плоская страница, без новых виджетов

`/app/repositories/:repositoryId/settings` (в `AppRouter` — `/repositories/:repositoryId/settings`
под `basename="/app"`), страница `src/pages/RepositorySettingsPage.tsx` —
плоско, как страницы кабинета, а не в подкаталоге. Каждый блок достаточно прост (форма antd
и панель), поэтому виджеты не заводим: страница компонует `features/repository` и
`entities/repository` напрямую. Рассмотрели `widgets/repository-settings` — отклонено: между
страницей и блоками нет композиции нескольких слайсов одного слоя, лишний слой только
добавил бы переэкспорты.

### Модели — схемы контракта, snake_case без маппинга

```ts
type SeverityLevel = 'low' | 'medium' | 'high' | 'critical' // FindingSeverity контракта, #28
type RepositorySettings = {
  auto_review_enabled: boolean
  branch_filter: string[] // glob-паттерны, например 'feature/**'
  min_severity: SeverityLevel
}
type RepositorySettingsUpdate = ApiSchemas['RepositorySettingsUpdate'] // тело PUT — тип контракта
type RepoRule = {
  name: string // раздел `##` в rules.md
  patterns: string[] // glob области действия
  excludes: string[] // glob исключения
  checks: string[] // нумерованные проверки
}
type RejectedRule = { name: string; reason: string }
type RulesLoadStatus = 'loaded' | 'empty' | 'absent' | 'too_large' | 'unavailable' // контракт
type RulesStatus =
  | {
      status: 'loaded'
      branch: string
      path: string
      rules: RepoRule[]
      rejected: RejectedRule[]
      fetched_at: string
    }
  | { status: 'empty'; branch: string; path: string; rejected: RejectedRule[]; fetched_at: string }
  | { status: 'absent' | 'too_large' | 'unavailable'; branch: string; path: string }
```

Поля — snake_case, как отвечает бэкенд: отдельного маппинга нет, тип выводится из Zod-схемы и
должен совпадать с контрактом. Совпадение проверяет компилятор: рядом со схемами —
`MatchesContract` против `RepositorySettingsResponse`, `RulesStatusResponse` и
`FindingSeverity` (`entities/repository/model/settings.ts`); разойдутся — упадёт typecheck.
`empty` — файл разобран, но ни один раздел не стал правилом; всё, кроме `loaded`, — дефолтный
фоллбэк «ревью по стандартным критериям». Порог severity — уровни `FindingSeverity` без
маппинга пресетов: согласовано в #28, merge gate (api#51) и вердикт «запрос изменений»
(api#54) читают один `min_severity` репозитория.

### Расположение по FSD

- `entities/repository`: `model/settings.ts` — Zod-схемы и типы настроек и статуса правил с
  проверкой против контракта; `lib/branchFilter.ts` — нормализация фильтра веток и лимиты
  контракта (не больше 50 паттернов по 200 символов); `ui/RulesStatusBadge.tsx` и
  `ui/RulesPreview.tsx` — бейдж и превью; `api/repositoryApi.ts` — функции по ручкам
  контракта: `fetchRepository` (`GET /repositories/{id}`), `fetchRepositorySettings` и
  `saveRepositorySettings` (`GET`/`PUT …/settings`), `fetchRulesStatus` (`GET …/rules`).
- `features/repository/model/repositoryQueries.ts` — ключи `['repositories', id, 'settings' |
'rules']`; `useRepository` по одной ручке `GET /repositories/{id}` — имя репозитория не
  ищется в первой странице списка, ложный 404 за её пределами невозможен;
  `useSaveRepositorySettings` кладёт ответ в кэш (`setQueryData`) и инвалидирует `settings`,
  `repository` и `connected`: флаг `auto_review_enabled` — одна колонка с
  `RepositoryResponse`, второй источник правды не заводится.
- Моки — `app/mocks/repositorySettings.ts` (стор настроек и статуса правил по ручкам
  контракта; `onAutoReviewChange` синхронизирует флаг авто-ревью в стор репозиториев, как это
  сделал бы бэкенд) и маршруты `app/mocks/mockAdapter.ts` (`GET`/`PUT …/settings`,
  `GET …/rules`).

Рассмотрели отдельный слайс `entities/rules` — отклонено: правила не существуют без
репозитория, а кабинет уже держит всё репозиторное в одном слайсе.

### Черновик формы — локальное состояние, кэш — только сохранённое

Несохранённый черновик живёт в antd `Form` (локальное состояние экрана), TanStack Query хранит
только сохранённые настройки. Zustand не заводим: значение нужно одному экрану. Значения
заливаются одним механизмом — эффектом `setFieldsValue` при смене `data` вне черновика (он
покрывает и первое заполнение, и синхронизацию после инвалидации); `initialValues` не нужен.
Блоки экрана рендерятся с `key={repositoryId}` и перемонтируются при смене репозитория:
черновик и данные одного репозитория не показываются у другого. Перед сохранением
`branch_filter` нормализуется (`normalizeBranchFilter`): пробелы по краям обрезаются, пустые
паттерны отбрасываются, повторы не сохраняются. На время мутации форма блокируется: `isPending`
длится до прихода инвалидированных данных, поэтому правки в момент сохранения невозможны, а
после разблокировки форма синхронизируется уже со свежим кэшем. При ошибке черновик остаётся
нетронутым. Сброс возвращает сохранённые значения и сбрасывает состояние мутации (`reset`),
чтобы баннеры успеха/ошибки не висели над откатанной формой.

### Ошибки блоков — фоновое обновление не выкидывает данные

Полная ошибка с повтором — только когда данных блока нет (первая загрузка); «Повторить»
показывается только для не-4xx — повтор клиентской ошибки ответа не изменит. Упавший фоновый
рефетч (`isError=true` при живом `data` в v5) не заменяет содержимое: блок показывает последние
загруженные данные, сверху — `ErrorState` с повтором. 404 заголовка экрана — `Result` «не
найден» и инвалидация списка подключённых. Отдельно различается 501: ручка блока, описанная в
контракте, но отвечающая заглушкой `NOT_IMPLEMENTED` (`isNotImplemented` из `shared/api`),
даёт в этом блоке заметку «пока недоступно» — как `ConnectRepositoryPage` и вкладка «Ревью»;
остальные блоки продолжают работать. Действует во всех блоках экрана и в списке репозиториев
страницы.

### Превью правил — текст и теги, без HTML

Ручка `GET …/rules` отдаёт уже распарсенные правила; проверки рендерятся текстом через
существующий `TextWithCode` (инлайн-код — моноширинно), паттерны `pattern`/`exclude` —
моноширинными чипами, отклонённые разделы — отдельным блоком с причиной из
`RejectedRule.reason`. Исходы без применимых правил — дефолтный фоллбэк: сообщение про
стандартные критерии; `empty` показывает отклонённые разделы с причинами, `absent` —
предложение создать `.review/rules.md`. Read-only достигается отсутствием полей ввода. Списки
превью не сортируются, а содержимое может повторяться (одноимённые разделы, одинаковые
проверки), поэтому React-ключи — по индексу, а не по содержимому. Рассматривали рендер
raw markdown библиотекой — отклонено при планировании: «превью распарсенных правил» из
задачи, и парсинг остаётся на бэкенде.

### Фикстуры

`repo-1` (`platform-api`) — `.review/rules.md` с правилами `Security`, `Performance`, `Style`
(форма `RepoRule` контракта) и отклонённым разделом `Docs`. `repo-2` (`docs`) — без файла
правил: исход `absent`, сценарий предупреждения с предложением создать файл. `repo-3`
(`design-system`) — файл разобран, но ни один раздел не стал правилом: исход `empty` с
отклонёнными разделами. Исходы `too_large`/`unavailable` не заводятся отдельными
репозиториями — их покрывают тесты компонентов. Настройки у репозиториев различаются, чтобы
форма не выглядела константой.

## Risks / Trade-offs

- [Моки разойдутся с контрактом] → фикстуры типизированы типами сущности, а те проверены
  `MatchesContract` против схем контракта: расхождение ловит typecheck и `pnpm api:check`;
  форму ответа во время работы проверяет `parseResponse` (расхождение — `ContractError` в
  своём блоке).
- [PUT полной заменой теряет поля] → тело сохранения — тип контракта `RepositorySettingsUpdate`
  со всеми тремя полями: форма отправляет полный набор, а `branch_filter` нормализуется перед
  отправкой, чтобы пустые и повторы не занимали лимиты контракта.
- [Ручки-заглушки 501] → 501 — ожидаемое состояние ручек блока: экран показывает «пока
  недоступно» в своём блоке и не выдаёт это за ошибку стенда.
- [Refetch затирает черновик формы] → форма обновляется из кэша только вне черновика (эффект
  `setFieldsValue` с защитой по `isDirty`), а на время сохранения блокируется — форма и кэш не
  расходятся.

## Migration Plan

Новый экран, ничего не выключается: откат — удалить маршрут и страницу. Данные мок-сторов
существуют только в памяти сессии и не требуют миграции.
