## Context

Бэкенд заменил поток одного прогона общим потоком кабинета `GET /api/v1/events` (dmc-268-api-t1#103, #115). У потока нет снимка в начале соединения и нет истории, события называются `<ресурс>.<действие>`, у `run.*` данные — `ReviewRunListItem`, а версии строки сравниваются по `updated_at`.

Этот change отменяет два решения из `design.md` change `review-run-live-status` (раздел «Контракт событий — предложение бэкенду»): первое событие соединения больше не снимок от сервера, и единого события `status` больше нет — вместо него `run.created`, `run.status_changed`, `run.finished`. Остальные решения того change (SSE без polling, `EventSource`, состояние соединения, таймаут тишины, видимость вкладки) остаются.

## Decisions

### Снимок через REST на `open`

На каждое `open` потока, первое и после переподключения, экран перезапрашивает `GET /reviews/{id}`. Это заменяет снимок, который раньше слал сервер: пропущенное до открытия и за время обрыва поток не повторит. Перезапрашивается только сам прогон (`invalidateQueries` с `exact: true`): ключи диффа и шагов начинаются с ключа прогона, а перекачивать дифф на каждое переподключение незачем.

«Обновить» после отказа только переоткрывает поток: снимок возьмёт `open` нового соединения, поэтому запрос прогона один, а не два.

### Правило `updated_at` для событий и для снимка

Из двух версий прогона побеждает та, у которой `updated_at` больше, при равном — пришедшая позже (правило контракта). Сравнение — с точностью до микросекунд: дробная часть дополняется до 6 знаков, и строки формата контракта (UTC с `Z`) сравниваются как есть; `Date.parse` режет до миллисекунд.

- Событие старше прогона в кэше отбрасывает `applyRunEvent`.
- Снимок тоже может опоздать: сервер прочитал прогон до события, а ответ пришёл после него. Запрос прогона сводит ответ с кэшем через `structuralSharing` (`mergeRunSnapshot`): если `updated_at` ответа меньше, статусные поля (`status`, `last_progress_at`, `failed_stage`, `duration_seconds`, `updated_at`) остаются из кэша, остальное — замечания, вердикт, причина сбоя — берётся из ответа. Правило живёт в запросе, а не в хуке подписки: через `structuralSharing` проходит любая запись в кэш, и второго состояния «последнее событие» не нужно.
- Итоговый перезапрос после `run.finished` несёт версию не старше события: при равном `updated_at` ответ применяется целиком.

### Фильтр по прогону и незнакомые типы

Экран берёт только события `run.*`, у которых `data.id` — его прогон. События других прогонов и незнакомых типов пропускаются молча: контракт разрешает серверу добавлять типы. Событие известного типа вне схемы пишется в консоль как `ContractError` и подписку не рвёт.

### Таймер тишины

Таймер тишины сбрасывают только слушаемые типы (`RUN_EVENT_TYPES`) и `ping`: контракт обещает `ping` в тишине. Если появятся частые незнакомые типы без `ping`, таймер надо будет сбрасывать любым событием.
