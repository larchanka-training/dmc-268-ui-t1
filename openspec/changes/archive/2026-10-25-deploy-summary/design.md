## Context

Бэкенд в api#210 сделал то же для своего деплоя: план в файл, сторож томов, разбивка простоя API по событиям Docker, summary с ключами OpenTelemetry. Фронт отличается: один контейнер `dmc268-ui` без проверки здоровья, без миграций и targeted apply, с томом ACME вместо томов данных; стек — Node, тесты — vitest.

## Goals / Non-Goals

**Goals:**

- Простой публичного входа в summary — с разбивкой и честными границами там, где точного значения нет.
- План с уничтожением тома ACME не доходит до apply.
- Summary фронта и бэкенда выглядят одинаково и пишутся одними ключами.

**Non-Goals:**

- Сокращать простой. Репетиция показала, куда он уходит (см. ниже), правки — отдельной задачей.
- Проверка здоровья контейнера интерфейса.

## Decisions

### Порт отчёта на Node, а не копия Python

`deploy_report.py` бэкенда — про API: healthcheck, миграции. Во фронте нет ни Python-тестов, ни Python в CI; есть прецедент `scripts/build-summary.mjs` и тесты скриптов в `.github/tests/*.test.mjs`. Общие части — сторож, счётчики плана, диск, засечки, шаги, ключи — перенесены тем же алгоритмом с пометкой «держать в синхроне». Байт в байт копируются `mark.sh` и `stand-ssh` — со сверкой `diff` в шапке.

### Готовность — первый ответ HTTPS снаружи

Проверки здоровья у `dmc268-ui` нет, и сервер о готовности nginx не сообщает. Готовность — время первого успешного ответа из шага проверки сайта. Он с часов раннера; `apply.sh` перед выкатом спрашивает у сервера `date` и засекает время раннера до и после — сдвиг часов с точностью до половины круга. Опрос начинается после apply и идёт раз в 3 с, поэтому значение — верхняя граница; если до успешной попытки были неуспешные, summary даёт и нижнюю. `/api/v1/` через прокси проверяется после проверок сайта — это тоже лишь верхняя граница, так и подписано.

Добавить healthcheck — точнее, но это смена поведения контейнера, не отчёта; оставлено открытым вопросом.

### Поток событий по типам, а не по контейнеру

Фильтры `docker events` разных ключей складываются через «и»: по имени контейнера `pull` образа не отобрать. Поток идёт по событиям `kill`, `die`, `destroy`, `create`, `start`, `pull`; чужие (параллельный деплой бэкенда) отсеивает отчёт по id контейнера и digest образа. `pull` считается частью простоя, только если он между выходом старого и созданием нового.

### Сторож по адресу и по имени тома

`prevent_destroy` уходит вместе с блоком ресурса. Если ресурс переименовали без `moved` и поправили `PROTECTED` под новый адрес, план уничтожает том по старому адресу, и сторож по одному адресу его бы пропустил. Поэтому сторож смотрит ещё и на `change.before.name` у `docker_volume`. Тест сверяет: каждый том из `infra/*.tf` — в `PROTECTED` с тем же именем и с `prevent_destroy`.

### Что показала репетиция

`docker:29-dind`, реальный образ интерфейса, OpenTofu 1.13.2. Замена образа идёт так: `kill` (SIGQUIT) → через 7 мс `kill` (SIGKILL) → `die` → `destroy` → `pull` нового образа → `create` → `start`. Значит:

- провайдер без `destroy_grace_seconds` удаляет контейнер с force: nginx не дорабатывает запросы и SSE, а запись ACME на том может оборваться;
- скачивание образа приходится на простой: `docker_image` заменяется между удалением старого контейнера и созданием нового. В репетиции из локального реестра это 0,08 с, с ghcr — секунды.

## Risks / Trade-offs

- [Параллельный деплой бэкенда пересоздаёт хранилище состояния `dmc268-s3`] → туннель фронта рвётся, и состояние после apply не записывается. `-lock-timeout` здесь не помогает: ключи состояния разные. Риск был и раньше, теперь он виден в summary шагом падения.
- [Продление ACME в момент выката] → SIGKILL может оборвать запись сертификата на томе. Сторож защищает от удаления тома, не от порчи файла.
- [Расхождение часов] → готовность переводится одним замером; при RTT 80 мс точность ±0,04 с, и она подписана в summary.
