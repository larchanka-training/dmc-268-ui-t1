## Context

См. `proposal.md` — Why. Приложение пока содержит стартовый экран и не имеет
browser API-контракта для данных ревью. Архитектурный документ фиксирует FSD,
mock adapter, unified Diff Viewer и границы будущей интеграции.

## Goals / Non-Goals

**Goals:**

- Реализовать проверяемый технический экран одного прогона на mock-данных.
- Сохранить границу adapter, чтобы HTTP-клиент можно было добавить без
  переписывания UI-компонентов.
- Разделить server state, общий UI-state и локальное состояние по правилам
  репозитория.

**Non-Goals:**

- HTTP API, авторизация, polling, deployment и Vite proxy.
- Side-by-side diff, подгрузка скрытых частей файла и исторические snapshots.
- Публикация комментариев в GitHub/GitLab и интерфейс полного trace worker.

## Decisions

### Mock adapter — единственный источник server state

TanStack Query получает агрегат одного прогона через типизированный mock
adapter и валидирует данные Zod до рендеринга. Ключ включает id прогона:
`['mock-review', runId]`.

Альтернатива — передавать литералы прямо в компоненты. Она не оставляет шва для
будущего API и смешивает транспорт с UI, поэтому не выбрана.

### Unified diff без скрытого context

`DiffViewer` рендерит один выбранный файл; `DiffHunk` выводит все переданные
removed, added и context-строки в исходном порядке. Context не скрывается и не
раскрывается: mock adapter не обещает отдать дополнительные участки файла.

Альтернатива — side-by-side и раскрываемые блоки context. Для них нужны правила
выравнивания строк и API для дополнительных фрагментов файла, поэтому они
отложены.

### Состояние разделено по области ответственности

`ReviewWorkspace` хранит в Zustand выбранный файл и фильтры severity, потому
что этими значениями совместно пользуются `FileList` и `DiffViewer`.
`RunInspector` хранит выбранное действие в локальном React state, так как оно
используется только его дочерними компонентами.

Хронология получает mock-действия из того же валидируемого агрегата прогона.
Inspector показывает только статус, длительность и очищенный preview; он не
обещает форму будущего API `review_run_actions`.

Альтернатива — один глобальный store. Она объединяет независимые виджеты и
увеличивает риск неявных зависимостей, поэтому не выбрана.

### Привязка finding ограничена изменённой строкой

`ReviewFinding` рендерится только когда его путь, сторона и номер строки
соответствуют added или removed строке diff. Context-строки не служат anchor.

## Risks / Trade-offs

- [Mock отличается от будущего API] → adapter и Zod-валидация изолируют
  транспортную границу; реальный DTO согласуется отдельным change.
- [Большой diff создаёт много DOM-узлов] → текущий viewer показывает один файл;
  виртуализация оценивается на реальных данных отдельной задачей.
- [Нет source diff у backend] → UI не обещает раскрытие или загрузку скрытых
  фрагментов файла.
