# Design

## Context

Бэкенд (#247, change `repositories-one-list`) свёл два списка в один и добавил выключение
ревью. Решения о поведении приняты в #95 и `docs/GITHUB_APP.md` бэкенда; здесь — только то,
что решает фронт.

## Decisions

### D1. Один запрос списка, `install_url` — из него же

`fetchRepositories` собирает все страницы (`offset += 200`, пока страница полная) и отдаёт
`{items, install_url}`, `install_url` из первой страницы; ключ кэша
`['repositories', 'list']`. Список и кнопка «Добавить» — из одного запроса, второго
источника правды нет. zod-схема строки — `RepositoryListItemSchema`, совпадение с контрактом
проверяет `MatchesContract`. `RepositorySchema` (`RepositoryResponse`) остаётся для
`GET /repositories/{id}` и ответа `POST`.

### D2. `install_url: null` — кнопки нет

Бэкенд отдаёт `null`, если не узнал slug приложения. Кнопку «Добавить репозитории из GitHub»
и крупную кнопку пустого списка тогда не показываем: неактивная кнопка с подсказкой ничего не
даёт пользователю, а адреса для перехода нет. Подсказка над таблицей и текст пустого списка
тогда не упоминают кнопку, которой нет.

### D2a. «Управлять доступом в GitHub» ведёт на `install_url`

Экран установки показывает аккаунты, где приложение уже стоит, с кнопкой Configure, в том
числе организации; `https://github.com/settings/installations` показывает только личный
аккаунт. Поэтому ссылка ведёт на `install_url`, а при `null` на
`https://github.com/settings/installations`. Ссылка открывается в той же вкладке: после
Configure GitHub возвращает на Setup URL (Redirect on update), то есть снова на эту страницу.

### D3. `409` и `204` — в мутации, а не в странице

`useConnectRepository` глотает `ApiError` `409` с `code = REPOSITORY_ALREADY_CONNECTED`: ревью
уже включено, в том числе параллельным запросом, — для пользователя это успех. `DELETE` уже выключенного бэкенд и так
отвечает `204`. Обе мутации инвалидируют список в `onSettled`, то есть и после ошибки:
строка могла измениться на сервере (выключили другие, сняли права). Без оптимистичного
обновления: переключатель крутит `loading`, пока идут запрос и перезапрос, и показывает то,
что ответил сервер.

Хук мутации один на все строки. Новый `mutate` снимает observer с предыдущей мутации, поэтому
страница вызывает `mutateAsync(v).catch(...)`, а спиннер строки строит из кэша мутаций:
`usePendingReviewToggles` — `useMutationState` по `mutationKey`
`['repositories', 'connect' | 'disconnect']` со статусом `pending`. Две строки, включённые
подряд, крутят спиннер каждая, и ошибка первой не теряется.

### D4. Подтверждение выключения — `Modal.useModal`, сообщения — `message.useMessage`

Хуки, а не статические `Modal.confirm` / `message`: статические вызовы не видят
`ConfigProvider` (тема, локаль). Включение подтверждения не требует: оно ничего не теряет.

### D5. Подсказка без прав — текстом рядом с переключателем

«Включать и выключать ревью может участник с ролью admin или maintain в этом репозитории»
(одна фраза: `can_connect` — то же правило у `POST` и `DELETE`) выводится вторичным текстом в
строке, а не всплывающей подсказкой: у неактивного элемента нет событий указателя и фокуса,
tooltip на нём не открылся бы ни мышью, ни с клавиатуры. Текст связан с переключателем через
`aria-describedby`.

### D6. Возврат с GitHub

Страница читает `connected`, `requested`, `setup_error` из query. Тексты:

| Параметр                                         | Сообщение                                                                        |
| ------------------------------------------------ | -------------------------------------------------------------------------------- |
| `connected=N`, N > 0                             | «Подключено репозиториев: N»                                                     |
| `connected=0` («All repositories» или Configure) | «Доступ в GitHub обновлён. Включите ревью переключателем в нужных репозиториях.» |
| `requested=true`                                 | «Запрос на установку отправлен владельцу»                                        |
| `setup_error=installation_not_found`             | «GitHub не нашёл эту установку среди ваших…»                                     |
| `setup_error=provider_unavailable`               | «GitHub не ответил…»                                                             |
| другой `setup_error`                             | «Не удалось завершить установку приложения на GitHub.»                           |

После показа параметры итога удаляются из URL заменой записи истории (остальные
параметры остаются), чтобы перезагрузка и «назад» не показывали итог повторно. Сообщение
открывается с ключом: повторный вызов эффекта в `StrictMode` заменяет его, а не дублирует.
Отдельный перезапрос списка не нужен: бэкенд уводит браузер на страницу полной загрузкой, а
внутри SPA данные в кэше сразу устаревшие (`staleTime` 0), и открытие страницы
запрашивает список.

### D7. Свитчер «Авто-ревью» убран, флаг в `PUT` уходит как был

Контракт `PUT …/settings` по-прежнему требует `auto_review_enabled`. Поле убрано из формы, а
в тело подставляется сохранённое значение из `GET …/settings`: настройка не меняется молча.

### D8. Соседи списка

«Обзор» считает строки с `connected: true`. Фильтр «Репозиторий» вкладки «Ревью» предлагает
строки с `id`: прогоны есть только у репозиториев с записью в сервисе, в том числе у
выключенных.

### D9. Поиск и фильтр на клиенте

Список и так загружается целиком, поэтому `q` и `only=enabled` фильтруют его на клиенте, без
запросов. Параметр `only`, потому что `connected` занят итогом возврата с GitHub. Серия записей
истории при наборе и своё состояние поля устроены так же, как были на удалённой странице подключения
(`ConnectRepositoryPage.tsx` в develop до этого change).

## Risks

- `DELETE` на стенде отвечает `501` до шага 2 бэкенда — пользователь видит «Выключение ревью
  пока недоступно»; mock adapter уже отвечает `204`.
- Дельта `cabinet-repository-settings` опирается на change `repository-settings`, который
  ещё не заархивирован: архивировать его нужно раньше этого.
