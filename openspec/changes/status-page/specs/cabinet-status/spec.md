# Spec Delta

## Purpose

Страница статуса сервиса: работает ли сервис сейчас и какая его часть сбоит.

## ADDED Requirements

### Requirement: Публичная страница статуса

Интерфейс SHALL отдавать страницу «Статус сервиса» по маршруту `/status` приложения
(`/app/status`) без проверки сессии. Страница SHALL брать данные из `GET /api/v1/status` и
SHALL NOT запрашивать профиль пользователя.

#### Scenario: Гость открывает статус

- **WHEN** пользователь без сессии открывает `/app/status`
- **THEN** страница показывает состояние сервиса
- **AND** интерфейс запрашивает только `GET /api/v1/status` и не уводит на вход

### Requirement: Общее состояние и компоненты

Страница SHALL показывать общее состояние и состояние трёх компонентов в порядке «API»,
«Обработка ревью», «Очередь задач». Под компонентами SHALL выводиться «Проверено: <время>» в
общем формате дат приложения.

#### Scenario: Воркер лежит

- **WHEN** API отвечает `status: outage`, `api: operational`, `worker: outage`, `queue: degraded`
- **THEN** общее состояние — «Недоступен», API — «Работает», «Обработка ревью» —
  «Недоступен», «Очередь задач» — «Работает со сбоями»

### Requirement: Состояние словом

Состояние SHALL выводиться словом: `operational` — «Работает», `degraded` — «Работает со
сбоями», `outage` — «Недоступен», `unknown` — «Нет данных»; цвет SHALL NOT быть единственным
признаком. Незнакомое состояние SHALL показываться как «Нет данных», компонент, которого нет в
ответе, — тоже.

#### Scenario: Мониторинг не настроен

- **WHEN** API отвечает `unknown` для всех компонентов
- **THEN** общее состояние и все компоненты — «Нет данных»

#### Scenario: Новое состояние у бэкенда

- **WHEN** API отвечает состоянием, которого интерфейс не знает
- **THEN** страница показывает «Нет данных», а не ошибку

### Requirement: Статус обновляется сам

Страница SHALL перезапрашивать статус раз в 30 секунд, пока вкладка видна, и при возврате на
вкладку, если с прошлого ответа прошло больше 15 секунд.

#### Scenario: Состояние изменилось

- **WHEN** страница открыта, и через 30 секунд API отвечает другим состоянием
- **THEN** страница показывает новое состояние без перезагрузки

### Requirement: Сбой запроса статуса

Если запрос статуса не удался, страница SHALL показывать состояние, а не пустой экран ошибки.
Если API не ответил — сбой сети или ответ `5xx`, в том числе `502` от nginx, — API SHALL
показываться «Недоступен», если ответил ошибкой `4xx` или ответом вне контракта — «Нет
данных». Обработка ревью и очередь задач SHALL показываться «Нет данных»: их состояние
сообщает только API. Общее состояние SHALL быть худшим из компонентов.

#### Scenario: Контейнер API остановлен

- **WHEN** `GET /api/v1/status` отвечает `502`
- **THEN** общее состояние — «Недоступен», API — «Недоступен», «Обработка ревью» и «Очередь
  задач» — «Нет данных»

### Requirement: Пояснение и повтор при сбое

При сбое запроса страница SHALL пояснять, что статус от API получить не удалось, и давать
проверить снова. Сбой очередного опроса SHALL заменять показанный ранее ответ.

#### Scenario: Проверить снова

- **WHEN** запрос статуса не удался
- **THEN** над компонентами — «Не удалось получить статус от API» и кнопка «Проверить снова»

#### Scenario: API упал между опросами

- **WHEN** страница показывает «Работает», и очередной опрос завершается сбоем сети
- **THEN** страница показывает API «Недоступен», а не прежнее «Работает»

### Requirement: Ссылки на статус

Боковое меню кабинета SHALL содержать пункт «Статус сервиса», ведущий на `/status`. Страница
входа SHALL содержать ссылку «Статус сервиса» на `/app/status`.

#### Scenario: Пункт меню

- **WHEN** пользователь выбирает «Статус сервиса» в боковом меню
- **THEN** открывается страница статуса

#### Scenario: Страница входа

- **WHEN** гость открывает `/login`
- **THEN** на странице есть ссылка «Статус сервиса» на `/app/status`
