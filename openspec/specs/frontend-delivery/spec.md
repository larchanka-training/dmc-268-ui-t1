# frontend-delivery Specification

## Purpose

Описывает контракт доставки интерфейса: откуда берётся собранная статика, в каком порядке применяются стеки, каким путём браузер попадает в API и где живёт состояние развёртывания. Доставка интерфейса опирается на стек бэкенда, поэтому часть требований — про границу между двумя стеками, а не про сам интерфейс.

## Requirements

### Requirement: Статика собирается до развёртывания, а не на сервере

Собранный образ интерфейса SHALL создаваться в процессе непрерывной интеграции и попадать на сервер готовым, по ссылке с digest образа. Тег образа SHALL указывать коммит и источник данных кабинета, но развёртывание SHALL NOT зависеть от тега. Развёртывание SHALL NOT собирать статику на целевом хосте.

#### Scenario: Развёртывание на удалённый хост

- **WHEN** развёртывание выполняется на сервер, а не на машину с исходным кодом
- **THEN** на сервер попадает готовый образ, и наличие исходников там не требуется

#### Scenario: Пересборка того же коммита с другими параметрами сборки

- **WHEN** тот же коммит собирается заново с другим значением параметра, который попадает в бандл (например, источник данных кабинета)
- **THEN** развёртывание забирает новый образ и пересоздаёт контейнер интерфейса

### Requirement: Стек интерфейса применяется после стека бэкенда

Стек интерфейса SHALL опираться на сетевое окружение, созданное стеком бэкенда, и не создавать его самостоятельно: два стека независимы по состоянию, но не по порядку применения.

Отсутствие этого окружения SHALL приводить к отказу с понятным сообщением до внесения изменений, а не к частично применённому стеку.

#### Scenario: Развёртывание на подготовленный сервер

- **WHEN** стек бэкенда уже применён
- **THEN** стек интерфейса применяется и подключается к тому же сетевому окружению

#### Scenario: Развёртывание на чистый сервер

- **WHEN** стек бэкенда ещё не применён
- **THEN** развёртывание интерфейса отказывается выполняться и сообщает о отсутствующем предусловии

### Requirement: Браузер обращается к API по тому же адресу, что и к интерфейсу

Запросы интерфейса к API SHALL проходить через тот же адрес, по которому отдаётся сам интерфейс, и перенаправляться к API внутри серверного сетевого окружения.

Браузеру SHALL NOT требоваться второй адрес, и настройка межоригинных запросов SHALL NOT быть условием работоспособности.

Путь запроса SHALL доходить до API без изменений: префикс `/api` и версию ставит само приложение, и перенаправление SHALL NOT их срезать или переписывать.

#### Scenario: Запрос к API из интерфейса

- **WHEN** загруженный интерфейс обращается к API
- **THEN** запрос уходит на тот же адрес и достигает API, не покидая сервер

#### Scenario: Путь запроса сохраняется

- **WHEN** интерфейс запрашивает `/api/v1/reviews`
- **THEN** API получает запрос на `/api/v1/reviews`, а не на путь без префикса

### Requirement: После развёртывания браузер получает новую версию интерфейса

Документ, с которого начинается загрузка интерфейса, SHALL отдаваться без долговременного кеширования. Файлы с содержимым, однозначно определяемым их именем, SHALL кешироваться надолго.

Развёртывание новой версии SHALL становиться видимым пользователю без ручной очистки кеша браузера.

#### Scenario: Повторный визит после развёртывания

- **WHEN** пользователь открывает интерфейс после того, как развёрнута новая версия
- **THEN** он получает новую версию, а не сохранённую с прошлого визита

### Requirement: Состояние развёртывания интерфейса отдельно от состояния бэкенда

Состояние развёртывания интерфейса SHALL храниться вне машины, которая выполняет развёртывание, и SHALL быть отделено от состояния стека бэкенда: применение одного стека SHALL NOT изменять состояние другого.

#### Scenario: Развёртывание с эфемерного исполнителя

- **WHEN** развёртывание запускается на исполнителе, создаваемом под один запуск
- **THEN** следующий запуск видит ранее созданные ресурсы интерфейса и не пытается создать их повторно

#### Scenario: Развёртывание бэкенда

- **WHEN** применяется стек бэкенда
- **THEN** состояние стека интерфейса остаётся неизменным

### Requirement: Сообщаемый адрес пригоден для обращения

Адрес развёрнутого интерфейса, который сообщает развёртывание, SHALL быть пригоден для обращения клиентом. Значение, задающее интерфейс привязки, SHALL NOT использоваться как имя хоста в этом адресе. Если стенд отдаётся по HTTPS, сообщаемый адрес SHALL использовать схему `https`.

#### Scenario: Привязка ко всем интерфейсам

- **WHEN** интерфейс публикуется на всех сетевых интерфейсах сервера
- **THEN** сообщаемый адрес указывает на обращаемое имя хоста, а не на адрес привязки

#### Scenario: Стенд с TLS

- **WHEN** развёртывание включает HTTPS
- **THEN** сообщаемый адрес начинается с `https://`

### Requirement: На стенд попадает только проверенный коммит

Автоматическое развёртывание интерфейса SHALL выполняться только для коммита, по которому успешно прошёл CI. Развёртывание SHALL NOT заменять на стенде более новый коммит более старым.

Ручной запуск развёртывания SHALL оставаться возможным без ожидания CI, но только из ветки `develop`: ручной запуск из другой ветки SHALL отклоняться до сборки образа.

#### Scenario: CI упал

- **WHEN** в `develop` попадает коммит, по которому CI завершился неуспешно
- **THEN** развёртывание не выполняется, и на стенде остаётся предыдущая версия

#### Scenario: CI старого коммита завершился позже

- **WHEN** CI по коммиту завершается успешно, но `develop` уже указывает на более новый коммит
- **THEN** развёртывание этого коммита пропускается, а новый коммит развёртывается после своего CI

#### Scenario: Ручной запуск из другой ветки

- **WHEN** развёртывание запускают вручную из ветки, отличной от `develop`
- **THEN** образ не собирается, развёртывание не выполняется, и на стенде остаётся текущая версия

### Requirement: Стенд отдаётся по HTTPS

Публичный адрес стенда SHALL отдавать интерфейс и API по HTTPS с сертификатом, который браузер принимает без предупреждений. Запрос по HTTP SHALL перенаправляться на HTTPS.

Сертификат SHALL выпускаться и продлеваться без участия человека и SHALL переживать повторное развёртывание: развёртывание SHALL NOT выпускать сертификат заново, если действующий ещё не истёк.

#### Scenario: Открытие стенда по HTTP

- **WHEN** пользователь открывает адрес стенда по `http://`
- **THEN** он перенаправляется на `https://` и получает интерфейс без предупреждений о сертификате

#### Scenario: Повторное развёртывание

- **WHEN** развёртывание выполняется, пока действующий сертификат не истёк
- **THEN** используется сохранённый сертификат, и новый не запрашивается

### Requirement: Ответы интерфейса несут заголовки безопасности

Каждый ответ сервера интерфейса в режимах HTTP и HTTPS — страницы, статика, редиректы, страница 404, ответы с ошибкой и проксируемые ответы API — SHALL содержать `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` и `Content-Security-Policy`.

Проверка маршрутов в CI и после развёртывания SHALL завершаться ошибкой, если заголовков нет.

#### Scenario: Открытие страницы

- **WHEN** браузер открывает лендинг, `/login` или кабинет под `/app/`
- **THEN** ответ содержит `X-Content-Type-Options`, `Referrer-Policy` и `Content-Security-Policy`

#### Scenario: Редирект и 404

- **WHEN** гость открывает `/app/` и получает редирект на вход, или запрашивает несуществующий адрес
- **THEN** ответ с редиректом или 404 содержит те же заголовки

#### Scenario: Переход на другой сайт

- **WHEN** пользователь переходит со страницы кабинета на сайт с другим адресом
- **THEN** в `Referer` уходит только адрес интерфейса, без пути и строки запроса

### Requirement: Политика содержимого разрешает только свои источники

`Content-Security-Policy` SHALL разрешать скрипты и запросы только к адресу интерфейса, картинки — ещё из `data:` и с `https://avatars.githubusercontent.com`. Inline-скрипты и `eval` SHALL NOT разрешаться; inline-стили SHALL разрешаться — их вставляет библиотека компонентов кабинета.

Политика SHALL запрещать встраивание страниц во фрейм, плагины, смену базового адреса и отправку форм на другой адрес. Страницы интерфейса SHALL работать под ней без нарушений в консоли.

#### Scenario: Страницы под политикой

- **WHEN** браузер открывает лендинг, `/login`, страницу 404 или кабинет под `/app/`
- **THEN** страница отображается полностью, и в консоли нет нарушений политики

#### Scenario: Встраивание во фрейм

- **WHEN** чужой сайт встраивает страницу интерфейса во фрейм
- **THEN** браузер отказывается её отображать

#### Scenario: Чужой скрипт

- **WHEN** в страницу попадает скрипт с другого адреса или inline-скрипт
- **THEN** браузер его не исполняет

### Requirement: Развёртывание отклоняет неверную конфигурацию до изменений на сервере

Развёртывание интерфейса SHALL останавливаться на этапе планирования, ничего не меняя на сервере, если ссылка на образ не содержит digest, если имя хоста для клиента пустое или совпадает с адресом привязки ко всем интерфейсам, или если при HTTPS порт HTTP на хосте не 80.

#### Scenario: Ссылка на образ без digest

- **WHEN** развёртывание получает образ интерфейса только с тегом
- **THEN** планирование завершается ошибкой проверки переменной, и контейнер интерфейса не пересоздаётся

#### Scenario: Адрес привязки вместо имени хоста

- **WHEN** имя хоста для клиента задано как `0.0.0.0` или пустой строкой
- **THEN** планирование завершается ошибкой проверки переменной

#### Scenario: HTTPS не на 80-м порту

- **WHEN** развёртывание включает HTTPS, а порт HTTP на хосте не 80
- **THEN** планирование завершается ошибкой проверки переменной
