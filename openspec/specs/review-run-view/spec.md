# review-run-view Specification

## Purpose

Экран одного прогона ревью: загрузка прогона по адресу, его шагов и диффа, состояния ошибок загрузки.

## Requirements

### Requirement: Ошибка загрузки прогона

Если первая загрузка прогона завершилась ошибкой, кроме `404`, — в том числе `502` с `code = SCM_UNAVAILABLE`, — экран SHALL показывать «Не удалось загрузить прогон» с кнопкой «Повторить». Если ошибкой завершился перезапрос уже загруженного прогона, экран SHALL оставлять прогон на экране и SHALL показывать над ним плашку «Не удалось обновить прогон» с кнопкой «Повторить».

#### Scenario: GitHub недоступен при первой загрузке

- **WHEN** пользователь открывает прогон, а `GET /api/v1/reviews/{review_run_id}` отвечает `502`
- **THEN** экран показывает «Не удалось загрузить прогон» с «Повторить», а после успешного повтора — прогон

#### Scenario: GitHub недоступен при перезапросе

- **WHEN** прогон на экране, пришёл `run.finished`, а перезапрос прогона отвечает `502`
- **THEN** прогон остаётся на экране, над ним плашка «Не удалось обновить прогон», а «Повторить» приносит итоговые замечания

### Requirement: Ошибка загрузки части прогона

Если дифф прогона не загрузился с ошибкой, кроме `404` и `501`, экран SHALL показывать прогон с замечаниями списком вместо области изменений. Если шаги прогона не загрузились с ошибкой, кроме `501`, — в том числе `404`, потому что `GET /steps` реализован и `404` значит «прогона нет», — экран SHALL показывать на месте «Хода прогона» «Не удалось загрузить ход прогона» с кнопкой «Повторить», прогон остаётся на экране. `501` у шагов SHALL по-прежнему скрывать блок.

#### Scenario: GitHub недоступен при загрузке шагов или диффа

- **WHEN** `GET /api/v1/reviews/{review_run_id}/steps` или `/diff` отвечает `502`
- **THEN** прогон на экране, ошибки на весь экран нет; без диффа замечания показаны списком без ошибки, а на месте «Хода прогона» — «Не удалось загрузить ход прогона» с «Повторить», после успешного повтора — шаги

#### Scenario: Шаги прогона, которого нет

- **WHEN** `GET /api/v1/reviews/{review_run_id}/steps` отвечает `404`
- **THEN** на месте «Хода прогона» — «Не удалось загрузить ход прогона» с «Повторить», а не пустое место

### Requirement: Ход прогона обновляется по событиям

Пока прогон идёт, экран SHALL перезапрашивать шаги прогона на каждой смене уже известного статуса из общего потока событий, без таймеров и опроса; при первой загрузке шаги SHALL запрашиваться один раз. Повтор этапа внутри одного статуса блок МОЖЕТ показать при следующей смене статуса. Если перезапрос уже загруженных шагов упал, экран SHALL оставлять прежние шаги и показывать над ними плашку «Не удалось обновить ход прогона» с «Повторить».

#### Scenario: Смена статуса

- **WHEN** прогон в статусе `analysing`, и поток присылает `run.status_changed` со статусом `publishing`
- **THEN** экран перезапрашивает `GET /api/v1/reviews/{review_run_id}/steps` один раз, и в «Ходе прогона» появляется новый шаг

#### Scenario: Первая загрузка идущего прогона

- **WHEN** пользователь открывает прогон в статусе `analysing`
- **THEN** `GET /api/v1/reviews/{review_run_id}/steps` запрашивается один раз

#### Scenario: Перезапрос шагов упал

- **WHEN** шаги на экране, приходит смена статуса, а перезапрос шагов отвечает `502`
- **THEN** прежние шаги остаются, над ними плашка «Не удалось обновить ход прогона» с «Повторить»

### Requirement: Непроверенные замечания показаны предупреждением

Если у прогона `verification = unavailable` (верификатор недоступен, ревью доведено без второго прохода), упавшие шаги `verifying` экран SHALL показывать предупреждением «не перепроверено» с пояснением, что замечания не перепроверены, без метки «ошибка» и кода. При другом итоге верификации упавший `verifying` SHALL оставаться ошибкой с кодом: неудачная попытка модели с удачным повтором тоже пишется упавшим шагом, но замечания проверены.

#### Scenario: Верификатор недоступен у завершённого прогона

- **WHEN** у прогона `verification = unavailable` шаг `verifying` в статусе `failed`
- **THEN** у шага метка «не перепроверено» и пояснение «Замечания не перепроверены», без метки «ошибка» и без кода ошибки

#### Scenario: Попытка с удачным повтором

- **WHEN** у прогона `verification = verified` шаги `verifying` — `failed` с кодом `LLM_TIMEOUT` и затем `completed`
- **THEN** у упавшей попытки метка «ошибка» и код, предупреждения «не перепроверено» нет

### Requirement: Прогон по адресу

Экран прогона SHALL открываться по адресу `/app/reviews/{id}`, где `{id}` — идентификатор прогона на бэкенде, и SHALL загружать именно этот прогон. Если прогона с таким идентификатором нет, экран SHALL показывать «Прогон не найден» без кнопки повтора.

#### Scenario: Прогон из адреса

- **WHEN** пользователь открывает `/app/reviews/3f2a9c1e-5b7d-4e21-9a8f-0c6d2b1e4f70`
- **THEN** экран загружает и показывает прогон `3f2a9c1e-5b7d-4e21-9a8f-0c6d2b1e4f70`

#### Scenario: Неизвестный прогон

- **WHEN** пользователь открывает `/app/reviews/{id}`, а бэкенд отвечает `404`
- **THEN** экран показывает «Прогон не найден», и кнопки «Повторить» нет

### Requirement: Фильтр по файлам

Интерфейс SHALL позволять сузить список изменённых файлов по подстроке пути без учёта регистра и SHALL позволять показать только файлы, в которых есть замечания под текущие фильтры замечаний. Если выбранный файл выпал из списка, SHALL выбираться первый оставшийся файл.

#### Scenario: Поиск по пути

- **WHEN** пользователь вводит `api/` в фильтр файлов
- **THEN** в списке остаются только файлы, в пути которых есть `api/`

#### Scenario: Только файлы с замечаниями

- **WHEN** пользователь включает «Только с замечаниями» при фильтре severity `critical`
- **THEN** в списке остаются только файлы, где есть замечания `critical`

#### Scenario: Выбранный файл скрыт фильтром

- **WHEN** выбран файл, который перестал подходить под фильтр
- **THEN** выбирается первый файл отфильтрованного списка

### Requirement: Поиск по тексту замечаний

Интерфейс SHALL позволять искать замечания по подстроке в тексте замечания и в предлагаемом коде без учёта регистра. Пустая строка поиска SHALL показывать все замечания.

#### Scenario: Совпадение в тексте

- **WHEN** пользователь ищет `sql`, а у замечания текст «Возможна SQL-инъекция»
- **THEN** замечание остаётся в диффе, а замечания без совпадения скрыты

### Requirement: Сочетание фильтров

Фильтры разных видов SHALL применяться вместе: замечание показывается, только если подходит под все. Severity между собой SHALL объединяться через «или». Счётчики в списке файлов SHALL считать замечания под фильтры, сводка прогона — все замечания. Интерфейс SHALL показывать, сколько замечаний показано из общего числа, и SHALL давать сбросить все фильтры одним действием. Фильтры SHALL сохраняться при обновлении данных прогона.

#### Scenario: Severity и текст вместе

- **WHEN** выбраны severity `high` и `critical` и введён поиск `token`
- **THEN** показываются только замечания `high` или `critical`, в тексте которых есть `token`

#### Scenario: Ничего не найдено

- **WHEN** под фильтры не подходит ни один файл
- **THEN** вместо списка показывается сообщение и кнопка «Сбросить фильтры»

#### Scenario: Обновление прогона не сбрасывает фильтры

- **WHEN** фильтры заданы, и прогон перезапрошен после завершения
- **THEN** фильтры и выбранный файл остаются
